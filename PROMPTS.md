## R1 — RESEARCH: TTS и выравнивание (нужен web-доступ)
=====================================================================
Вход: PROJECT_CHARTER.md

Ты — инженер аудио-пайплайнов. Задача: исследовательский отчёт о TTS
с таймкодами для видеодвижка из Charter. НЕ проектируй архитектуру —
только факты и проверенные практики.

Ответь на вопросы, используя официальную документацию и реальные
issue-трекеры (давай ссылки):
1. ElevenLabs /with-timestamps: точные лимиты длины текста по моделям;
   формат alignment (original vs normalized); какие случаи ломают
   соответствие исходный текст ↔ нормализованный (числа, даты,
   аббревиатуры, кавычки, аудио-теги v3).
2. Известные проблемы точности/дрейфа таймкодов; поведение на паузах.
3. Чанкование длинного текста: request stitching (previous/next_text),
   правильная сшивка аудио без дрейфа (mp3 encoder delay — детали).
4. Forced Alignment API (ElevenLabs и альтернативы: WhisperX, Gentle,
   aeneas): точность, скорость на CPU, пригодность как контрольная
   проверка дрейфа субтитров (Charter AC5).
5. Альтернативные TTS с таймкодами (включая локальные) — таблица:
   качество EN-голоса / таймкоды / цена / CPU-реалистичность.
6. Какой минимальный интерфейс TTS-провайдера покрывает всё выше
   (только сигнатура, без реализации).

Правила: каждое утверждение помечай FACT (ссылка) / PRACTICE /
INFERENCE / UNKNOWN. Не выдумывай. Если данных нет — UNKNOWN.
Выход: один файл docs/research/r1-tts-alignment.md.

Ты — инженер систем рендеринга. Задача: выбрать рендер-архитектуру
для движка из Charter. Remotion — кандидат, НЕ решение по умолчанию.

Сравни минимум: Remotion, Motion Canvas, «свой Canvas/WebGL + ffmpeg

- delayRender/таймауты, шрифты, staticFile — чек-лист граблей.

Итог: RECOMMENDED RENDERING ARCHITECTURE + почему + trade-offs +
что заложить в архитектуру сейчас, чтобы не переписывать при переходе
на long-form (Charter §7 исходного замысла: 10–20 мин).
Правила пометок: FACT (ссылка) / PRACTICE / INFERENCE / UNKNOWN.

   что он должен проверять и о чём предупреждать (не «обход», а
   помощь в оригинальности — Charter V11).

выпиши, какие выводы могут устареть за 6 месяцев.

## A1 — CORE ARCHITECTURE
=====================================================================
Вход: PROJECT_CHARTER.md + r1 + r2 + r3

Ты — Principal Architect. Спроектируй ЯДРО движка из Charter.
Проектируй ТОЛЬКО необратимые решения:
1. Domain model (Project, Scene, Track, Asset, Caption, Marker, …):
   для каждой сущности — ответственность, входы/выходы, чего она
   НЕ должна знать.
2. Source format (что пишет человек/ИИ: сценарий с маркерами? свой
   DSL? markdown+yaml?) и пайплайн Source → компиляция → Video IR.
   Докажи или опровергни необходимость AST/IR.
3. Модель таймлайна: слои времени (слова/биты/сцены/главы против
   кадров/секунд), правила округления к кадрам, предотвращение дрейфа.
4. Project format на диске: файлы, schemaVersion, миграции,
   generated vs overrides (Charter V2), что в git / что в кэше.
5. Кэш по содержимому: что кэшируется, из чего состоит хэш,
   инвалидация.
6. Детерминизм: где живёт seed, иерархия seed'ов, как тестируется (AC4).
7. Граница рендерера: точный контракт «что рендерер получает»
   (Charter V9), сегментация по главам (V4).
8. Структура монорепо и зависимости пакетов (направление стрелок).

Правила:
- Формат каждого фундаментального решения: CURRENT IDEA → PROBLEM →
  ALTERNATIVES → RECOMMENDED → WHY → TRADE-OFFS, и отдельный ADR-файл.
- Решения V1–V11 из Charter не пере-изобретай молча; оспаривание —
  только явное: «оспариваю Vn, потому что…».
- Всё из Anti-scope Charter'а — максимум один абзац «дверь не закрыта,
  потому что…».
- Не пиши код, кроме сигнатур типов/интерфейсов.
- Не уверен — пиши UNKNOWN и что нужно проверить прототипом.
- В конце — раздел SPIKE LIST: 3–5 маленьких прототипов (по ≤1 дню),
  которые надо сделать до начала реализации, чтобы снять UNKNOWN'ы.
- И финальный вопрос: «если можно изменить одно решение в этом же
  документе — какое и почему» (самокритика).

Выход: docs/architecture/core.md + docs/adr/NNN-*.md (по файлу на решение).

Чек-вопросы для приёмки (я проверю сам):
- Могу ли я по документу объяснить путь «правка одного слова сценария →
  что пересчитается, что возьмётся из кэша»?
- Что произойдёт при регенерации TTS со всеми ручными правками?
- Как один и тот же проект отрендерить сегментами и получить AC4?

Вход: репозиторий; ИИ сам читает Charter, roadmap, релевантные ADR.

Задача: реализовать модуль «<ИМЯ МОДУЛЯ>» согласно docs/roadmap.md,
пункт <N>.

Правила:
1. Сначала прочти PROJECT_CHARTER.md, релевантные ADR и существующий
   код зависимостей. Составь план из 3–7 шагов, покажи мне, жди «ок».

3. Код приходит с тестами (unit + при необходимости интеграционный
   на фикстуре fixtures/minimal). Тесты пишутся вместе с кодом.
4. Запрещено нарушать V1–V11 из Charter. Сомневаешься — спроси.
5. Никаких новых зависимостей без обоснования в одну строку.
6. В конце: прогони тесты и рендер фикстуры, покажи вывод; перечисли,
   какие доки обновил; перечисли известные ограничения (честно).

=====================================================================
Вход: репозиторий + дифф модуля (git diff или ветка)

Ты — строгий ревьюер, не автор кода. Проверь дифф модуля «<ИМЯ>»:
1. Соответствие Charter (особенно V1–V11) и ADR — построчно там,

как исправить. Хвалить запрещено. Нет находок вообще — значит плохо
искал, ищи глубже.
