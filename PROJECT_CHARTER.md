# PROJECT CHARTER — Video Production Engine

<!-- Этот файл прикладывается К КАЖДОЙ сессии с ИИ. Это конституция проекта.      Менять его можно только осознанно, отдельным коммитом с объяснением. --> ## 1. Миссия

Детерминированный локальный движок производства видео: сценарий + голос + изображения + стиль → готовый YouTube Short (позже — long-form). ИИ (LLM) — внешний слой (пишет драфты сценариев, brief'ы). Ядро работает без ИИ.

## 2. Кто строит

Один разработчик, обычный ноутбук (CPU, умеренная RAM, без гарантии GPU). Local-first, single-machine. Без microservices/K8s/облака. Архитектура должна позволить позже вынести рендер-воркер в облако — не более.

## 3. Acceptance criteria (измеримые, версия 1 — можно уточнять)

* AC1: из сценария (\~150 слов) + 8 фото → публикуемый 60-сек Short.
* AC2: финальный рендер 60-сек Shorts ≤ 15 минут на моём ноутбуке.
* AC3: правка одной сцены → пересборка затронутой части ≤ 3 минут (draft).
* AC4: фикстурный проект, отрендеренный дважды, даёт одинаковые кадры (детерминизм проверяется автоматически).
* AC5: рассинхрон субтитров с речью ≤ 80 мс на любой минуте (проверяется forced alignment'ом финального аудио).
* AC6: старый проект открывается новой версией движка (миграция формата).

## 4. Валидированные решения (менять только с явным контраргументом)

Эти решения уже прошли анализ. ИИ-сессия НЕ пере-изобретает их молча; оспорить можно, но только явно: «оспариваю решение N, потому что …».

* V1. Тайминги эффектов/правок привязываются к word anchor id (якорям слов), НИКОГДА к абсолютным секундам. Регенерация TTS меняет все секунды.
* V2. Ручные правки живут в отдельном overrides-слое (patch поверх generated-артефакта). Generated-файлы регенерируемы и не правятся руками.
* V3. Шаблоны/композиции хранятся как вызов с параметрами ({template, params}), разворачиваются при рендере. Материализация в примитивы — только явный ручной "eject".
* V4. Инвариант сегментируемости: ни один эффект, звук или анимация не пересекает границу главы ([chapter]). Главы рендерятся независимо и конкатенируются.
* V5. Маркеры вырезаются из текста ДО отправки в TTS; нужен алигнер original ↔ normalized текста (числа, даты, аббревиатуры) с тестами.
* V6. Сшивка аудио-чанков — в PCM/WAV, кодирование один раз в конце (mp3 encoder delay даёт накопительный дрейф).
* V7. Схема проекта имеет schemaVersion + миграции с первого дня.
* V8. Детерминизм: запрещены Math.random, Date.now, нестабильные сортировки в рендер-пути; только seeded random.
* V9. Renderer «глупый»: во время рендера нет сети, TTS, поиска ассетов, бизнес-логики. Всё precomputed.
* V10. У каждого ассета — provenance (источник, лицензия, checksum). «Найдено в интернете» ≠ «можно использовать».
* V11. Не строим систему обхода YouTube-детекции. Строим систему, помогающую делать реально оригинальный контент (Policy Guard предупреждает, человек решает). Сценарии: ИИ-драфты + моя редактура.

## 5. Anti-scope (сейчас НЕ проектировать глубже одного абзаца)

Semantic Director, Creative Memory, Analytics-петля, Plugin System, Thumbnail Engine, мультиязычность, мультиканальность, полноценный таймлайн-редактор (Premiere-клон), realtime-превью несуществующих эффектов. Причина: их правильный дизайн невозможен до первых \~30 роликов. В архитектуре достаточно не закрыть им дверь.

## 6. Технологические предпочтения (гипотезы, оспоримы на этапе Research)

TypeScript, монорепо (pnpm workspaces), zod-схемы, SQLite, Remotion как кандидат в рендереры (подтвердить/опровергнуть в Research R2), ElevenLabs как первый TTS-провайдер за интерфейсом провайдера.

## 7. Правила работы с ИИ-сессиями

* Одна сессия = одна задача. Новый чат на каждый этап/модуль.
* К сессии всегда прикладываются: этот файл + релевантные ADR/доки.
* Результат сессии — файлы в репозитории (md/код/тесты), не текст в чате.
* Утверждения помечаются: FACT (с источником) / PRACTICE / INFERENCE / UNKNOWN. Выдумывать запрещено.
* Фундаментальные решения оформляются как ADR: Context → Decision → Alternatives → Consequences.
* Сессия деградировала (повторяется, теряет контекст, противоречит charter'у) → остановить, зафиксировать сделанное, начать новую сессию с коротким саммари. Не «дожимать» уставшую сессию.

## 8. Definition of Done для любого этапа

1. артефакты лежат в репо и закоммичены; 2) тесты/проверки этапа зелёные;
2. фикстурный проект рендерится; 4) доки/ADR обновлены; 5) я лично посмотрел результат глазами (для видео — на телефоне).
