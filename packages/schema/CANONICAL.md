# Каноническая форма — спецификация

**Зачем этот файл.** Обе канонизации живут в коде, но код — не спецификация: по нему нельзя
написать вторую реализацию, не читая его целиком, и нельзя проверить чужую. Ограничение №1
отчёта [`S-01`](../../docs/impl/S-01/report.md) называло это прямо. Здесь — то, по чему вторую
реализацию написать можно.

**Канонизации ДВЕ, и путать их нельзя.**

| | `canonicalJson` (`S-01`) | `writeFamily` / `renderFamily` (`S-02`) |
|---|---|---|
| зачем | вход **хэша** | файл в **git** |
| кто читает | машина: ключи кэша (ADR-0006 §2), `chunkKey`/`voiceKey` (ADR-0010 §3a), `roleDigest` (V15) | человек, в диффе на ревью |
| порядок ключей | **байты UTF-8** | **порядок объявления в схеме** |
| пробелы | нет ни одного незначимого | отступы есть, они значимы для YAML |
| комментарии | невозможны | **теряются** (см. «Ограничение») |
| ошибки | `NaN`, `±Infinity`, `-0`, `undefined`, `Map`, `Set`, `Date`… | всё, что отвергает схема семейства |

Алфавитный порядок в файле формата был бы прямым вредом: `width` уехал бы от `height`, `fps` —
в середину. Порядок объявления в схеме — это порядок, в котором величины объяснены в ADR.

---

## 1. `canonicalJson(value) → string`

Вход — значение JavaScript. Выход — строка. Алгоритм полностью:

1. **`null`** → `null`. **`true`/`false`** → `true`/`false`.
2. **Число.** `NaN`, `+Infinity`, `-Infinity`, `-0` — **ошибка** с путём. Иначе — запись
   ECMAScript `Number::toString` (кратчайшая, из которой значение восстанавливается
   однозначно): `1e21` → `1e+21`, `5e-7` → `5e-7`, `0.1` → `0.1`.
3. **Строка** → JSON-экранирование по ECMA-262 `QuoteJSONString` (двойные кавычки; `"`, `\`,
   `\b`, `\f`, `\n`, `\r`, `\t` — короткими escape'ами; прочие `U+0000…U+001F` и одиночные
   суррогаты — `\uXXXX`; всё остальное — как есть, UTF-8).
4. **Массив** → `[` элементы через `,` `]`. Порядок элементов **значим и не меняется**.
5. **Объект** — только plain-объект (прототип `Object.prototype` или `null`). Ключи
   сортируются **байтовым компаратором UTF-8** (см. §1.1), затем
   `{` `"ключ":значение` через `,` `}`.
6. **Ошибка с путём** (`$`, `$.a`, `$.a[0]`): `undefined`, `bigint`, `symbol`, функция, `Map`,
   `Set`, `Date`, `RegExp`, экземпляр класса, цикл в структуре.

Между токенами **нет ни одного пробела**. Результат — валидный JSON.

### 1.1 Байтовый компаратор UTF-8

Обе строки кодируются в UTF-8; сравниваются байты по порядку; при равном префиксе короче —
меньше.

**Это НЕ то же, что `a < b` в JavaScript** и не то же, что RFC 8785 (JCS): там порядок по
UTF-16 code units. Расхождение проявляется на ключах с астральными символами: `U+FFFF` — это
UTF-8 `EF BF BF`, а `U+1D11E` — `F0 9D 84 9E`; по UTF-16 суррогат `D834` **меньше** `FFFF`, по
UTF-8 `F0` **больше** `EF`. Порядок противоположный. Реализация обязана сравнивать байты.

### 1.2 Идемпотентность

`canonicalJson(JSON.parse(canonicalJson(v))) === canonicalJson(v)` для любого допустимого `v`.

## 2. `renderFamily(family, value) → string`

Вход — имя семейства и значение. Значение **обязано пройти схему семейства**: писатель не
создаёт файлов, которые читатель отвергнет.

### 2.1 Общее для всех форматов

* кодировка UTF-8, переводы строк `\n`, файл заканчивается одним `\n`;
* хвостовых пробелов нет ни в одной строке;
* **комментариев нет** — писатель их не порождает и не сохраняет;
* шапка `schema: <семейство>/<версия>` — **первой строкой** (в JSON — первым ключом).

### 2.2 Порядок ключей

1. сперва ключи, **объявленные схемой**, в порядке их объявления, но только те, что есть
   в значении;
2. затем ключи, схемой не объявленные (открытые карты: `aliases/1`, `direction/1 → params`) —
   **байтовым компаратором UTF-8** из §1.1.

Для union (например `direction/1`, где запись `track: voice` отличается от записи шаблона)
ветка выбирается **по значению**: та, чей разбор проходит.

### 2.3 Скаляры в YAML

* `null` → `null`; `true`/`false` → `true`/`false`; число → ECMAScript `Number::toString`;
* строка → **в двойных кавычках**, если выполнено хотя бы одно:
  * поле помечено в схеме как идентификатор (`vpeIdentifier`) — это инвариант **P17**;
  * строка пустая, начинается или кончается пробелом;
  * начинается с одного из `- ? : , [ ] { } # & * ! | > ' " % @ \``;
  * содержит `: ` , ` #`, перевод строки или табуляцию;
  * читается YAML не как строка: `true`/`false`/`null`/`~`, любое число (включая `0o…`, `0x…`);
  * читается как строка в YAML 1.2, но **не** в YAML 1.1: `yes`/`no`/`on`/`off`/`y`/`n`,
    шестидесятеричное `04:30`.

Последний пункт — защита **P16** со стороны писателя: он не создаёт значений, которые
чужой парсер прочитает другим типом.

### 2.4 Структура YAML

* маппинг: `ключ: значение` для скаляров; `ключ:` и вложенный блок с отступом **два пробела**
  для маппингов; `ключ:` и список **на том же отступе** для списков;
* пустые: `ключ: {}` и `ключ: []`;
* список: `- значение` для скаляров; `-` и блок с отступом два пробела для остального;
* flow-стиля (`{a: 1}`, `[1, 2]`) писатель не порождает **никогда**, кроме пустых.

### 2.5 JSON и JSONL

* **JSON** (`asset-record/1`): отступ два пробела, `": "` между ключом и значением, порядок
  ключей — из §2.2, экранирование строк — из §1.3, завершающий `\n`;
* **JSONL** (`anchors/1`): первая строка — `{"schema":"<семейство>/<версия>"}`, дальше по
  записи на строку в компактной форме (без пробелов), порядок ключей — из §2.2, завершающий
  `\n`. Форма шапки — `INFERENCE`: ADR-0005 §3 требует шапку, но не называет её синтаксис для
  JSONL; объект первой строкой — единственная форма, при которой файл остаётся валидным JSONL
  целиком.

### 2.6 Чего писатель не делает

* **не пишет `source-dialect/1`.** Схема этого семейства — только шапка, тело читает лексер;
  писатель вернул бы файл из одной строки, то есть уничтожил бы сценарий (M7). Попытка —
  ошибка, а не пустая операция;
* **не сохраняет комментарии** (см. ниже).

## 3. `checkCanonical(path)`

Возвращает список расхождений и — отдельным полем — **список выполненных проверок**, чтобы
зелёный отчёт нельзя было прочитать шире, чем он есть.

| проверка | как | на чём |
|---|---|---|
| `trailing-whitespace` | регулярное выражение по строкам текста | все форматы |
| `comment` | обход дерева документа: `commentBefore`/`comment` на узлах — **не грепом по `#`**, потому что `#` бывает внутри строки | YAML |
| `identifier-quoting` | **тип узла** (`PLAIN` против `QUOTE_*`) у полей, помеченных `vpeIdentifier` — не по содержимому | YAML |
| `key-order` | сравнение с порядком §2.2 на всех уровнях | YAML |
| `other` | текст отличается от канонического, а первые четыре ничего не нашли | всё, что писатель умеет писать |

Ни одной эвристики «похоже на …».

## 4. Ограничение, которое обязано быть прочитано: комментарии

**Писатель комментарии теряет.** Он строит текст из значения, а в значении комментариев нет.

Практическое следствие уже наступило: **`fixtures/minimal` не каноничны**, и `checkCanonical`
на них честно краснеет. Приводить их к канону **нельзя** — это уничтожило бы около сотни строк
объяснений со ссылками на ADR, номерами `FACT` из спайков и зафиксированными `UNKNOWN`, а
README фикстуры называет её «спецификацией формата в исполнимой форме». Решение владельца
(`S-02`, 2026-08-22): фикстуры не трогать, расхождение считать **видимым долгом**.

Замеренный дифф (`FACT`, `S-02`): `comment` — 90, `identifier-quoting` — 12, `key-order` — 5
(**только** в открытых картах), `other` — 4 (записи JSON), `trailing-whitespace` — 0.

Вопрос «канон обязан уметь комментарии» адресован владельцу и решается в `L-03` вместе с
`vpe fmt`. Пока он открыт, `vpe fmt --check` **нельзя** включать в CI на `fixtures/**`.
