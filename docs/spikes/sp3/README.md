# SP-3 — «Remotion: детерминизм и бюджет кадров»

Спайк из `docs/architecture/core.md §16`. **Блокирующий**: до его результатов ADR-0006 и ADR-0007
имеют статус `proposed`, а AC2 не обеспечен ничем, кроме отсутствия патологий
(`docs/adr/0008-renderer-boundary.md`, «Бюджет AC2»).

**Код этого каталога — одноразовый.** Он не входит в пакеты монорепо, не имеет тестов и
выбрасывается после того, как ответы получены. Остаются **артефакты замеров** в `results/`.

---

## 2. Как запустить

```bash
cd docs/spikes/sp3
npm install                 # remotion 4.x, react 19; Chrome Headless Shell скачается сам

node machine.mjs            # results/machine.json — железо, версии, питание
node bundle-bench.mjs       # results/raw/bundle.json — холодный/тёплый бандл + воспроизводимость
node bench.mjs              # матрица 12 прогонов → results/raw/*.json, results/summary.md
node extra.mjs              # concurrency 8 и прогон под нагрузкой CPU (core.md §16)
node determinism.mjs        # блоки A–D → results/raw/determinism.json + framemd5
node angle-c1-c2.mjs        # блоки J–L → results/raw/angle-determinism-c1-c2.json
node battery-run.mjs        # только при выдернутом шнуре — см. §4а
node mains-control.mjs      # только при воткнутом шнуре — контроль к battery-run
```

Флаги `bench.mjs` (по умолчанию — полная матрица):

```bash
node bench.mjs --gl=swangle,angle --concurrency=1,2,4 --profile=final,draft --timeout=1500
node bench.mjs --gl=angle --concurrency=4 --profile=draft     # один прогон
node determinism.mjs --only=C,D --repeats=3                     # только изоляция Chrome и энкодера
```

Порядок важен только для `bundle-bench.mjs` (он готовит тёплый бандл, которым потом пользуются
все прогоны) и для `determinism.mjs --only=D,E` (им нужен PNG-сиквенс из блока C).
`png-c1-repeat.mjs` дописывает блок F в уже существующий `results/raw/determinism.json`,
поэтому запускается после `determinism.mjs`.
`angle-c1-c2.mjs` пишет **свой** файл `results/raw/angle-determinism-c1-c2.json` и ни один
существующий не трогает; ему нужны уже снятые `results/raw/angle-4-final.json` (эталон mp4 при
c=4) и блок G в `determinism.json` (эталон PNG). Перед стартом он проверяет питание и, если
ноутбук на батарее, ждёт шнур (до 15 минут, `--wait-ac=`) — этот долг снимается **от сети**,
в отличие от `battery-run.mjs`.

**Результаты дописываются по мере прогона.** Файл `results/raw/<runId>.json` создаётся в статусе
`RUNNING` до начала рендера, `results/progress.jsonl` пополняется строкой на каждый завершённый
прогон, `results/summary.md` пересобирается после каждого. Обрыв замера на середине не теряет
уже сделанное; упавшая конфигурация получает статус `FAILED` с причиной и не мешает остальным.

### Сеть

Сети во время рендера быть не должно (V9). В спайке это обеспечено тем, что `ensureBrowser()`
вызывается с `onBrowserDownload`, который **бросает исключение**: если бы браузер не был скачан
заранее, прогон упал бы, а не ушёл бы тихо в сеть. Жёсткую проверку можно провести так:

```bash
unshare -rn --map-root-user sh -c 'ip link set lo up; node runner.mjs "{...}"'
```

Loopback поднимать обязательно: Remotion отдаёт бандл через локальный HTTP-сервер.

## 3. Что означает каждая колонка `results/summary.md`

### Таблица «Матрица прогонов»

| колонка | смысл | тонкость, без которой число врёт |
|---|---|---|
| `gl` | графический бэкенд Chrome: `swangle` (софтверный растеризатор) или `angle` | `FACT` r2 §7.4 п.5: `angle` использует GPU «when available», поэтому число зависит от машины; `swangle` — нет |
| `concurrency` | сколько вкладок Chrome рендерят кадры параллельно | это НЕ `chapterParallelism` (тот в v1 равен 1); параллелизм внутри одного сегмента |
| `профиль` | `final` (crf 18, scale 1) или `draft` (crf 28, scale 0.5) | различаются ровно двумя полями, всё прочее общее — иначе разница не приписывается фактору |
| `кадров/с` | **фаза рендера**: от готовности Chrome до готового mp4, включая энкод и мукс | именно это число сравнивается с порогами ADR-0008 |
| `wall-time, с` | весь процесс целиком: boot node + тёплый бандл + старт Chrome + рендер + мукс | на 60-сек ролике из ~8 сегментов эта разница оплачивается 8 раз |
| `пик RSS, МБ` | сумма `VmRSS` по всему дереву процессов (node + вкладки Chrome + ffmpeg) | завышает: общие страницы Chrome считаются многократно. Честная нижняя оценка — `Pss`, она в raw-JSON (`memory.peakPssSumMb`) |
| `детерминизм` | совпал ли `framemd5` с прогоном `concurrency=1` того же (gl, профиль) | **не** читается как «инвариантность к concurrency»: блоки C/E/F показали, что кадры меняются от прогона к прогону и при `concurrency=1`. Колонка говорит лишь, выпал ли прогон в тот же вариант, что эталонный |

### Таблица «Из чего складывается wall-time»

| колонка | смысл |
|---|---|
| `boot node` | старт процесса node и ESM-импорты — часть оверхеда на сегмент |
| `тёплый бандл` | `bundle()` при существующем кэше; холодный — в `results/raw/bundle.json` |
| `старт Chrome (проба)` | `openBrowser()` первым действием процесса. Возвращает управление рано, поэтому как «оверхед на сегмент» читать нужно следующую колонку |
| `до первого кадра` | boot node + бандл + композиция + запуск рендера. **Это и есть оверхед на сегмент** из ADR-0008 |
| `рендер кадров` | от первого кадра до последнего, без хвоста мукса |
| `хвост мукса` | от последнего отрендеренного кадра до готового файла |
| `framemd5` | полное декодирование сегмента ради AC4. ADR-0006 §14 выносит это во флаг `--verify-frames` и ночной прогон — здесь видно, почему |
| `ffprobe` | `StreamFingerprint` сегмента; в проде снимается только с первого сегмента и с финала |

### Таблица «Экстраполяция на AC2»

1800 кадров = 60 c при 30 fps, поделённые на измеренные кадры/с. Экстраполяция **линейна и потому
оптимистична**: она не учитывает, что ролик — это ~8 сегментов, то есть ~8 стартов процесса и
Chrome (колонка «до первого кадра») и ~8 холодных JPEG-декодов фона.

### Раздел «Детерминизм»

Четыре независимых блока, и их нельзя смешивать:

| блок | что запускается | что доказывает |
|---|---|---|
| **A** | `final`/swangle/concurrency 4, 3 прогона подряд | повторяем ли **прод** |
| **B** | профиль `ac4` (`render.ac4.yaml`: png-кадры, encoder threads 1, concurrency 1), 3 прогона | выполним ли **AC4** на выделенном профиле |
| **C** | `renderFrames` в PNG **без энкода**, 3 прогона | детерминирован ли **Chrome** (сравнение побайтовое и по framemd5) |
| **D** | один и тот же PNG-сиквенс → mp4 дважды, при `threads` 1 и 4 | детерминирован ли **энкодер** |
| **E** | PNG-сиквенс при `concurrency` 1 против 4, энкодера нет | зависит ли **Chrome** от `concurrency` |
| **F** | PNG-сиквенс при `concurrency=1`, 3 прогона подряд | детерминирован ли **Chrome** сам по себе на полном масштабе |
| **G** | PNG-сиквенс на `gl=angle`, c=4, 3 прогона | зависит ли ответ от графического бэкенда |
| **H** | готовый mp4 на `gl=angle`, c=4, 3 прогона | воспроизводится ли **то, что уходит в публикацию** |
| **I** | то же, что H, но при шести занятых потоках | держится ли ответ на занятой машине |
| **J** | готовый mp4 на `gl=angle`, c=1, 3 прогона | повторяем ли `angle` при `concurrency=1` |
| **K** | готовый mp4 на `gl=angle`, c=2, 3 прогона | повторяем ли `angle` при `concurrency=2` |
| **L** | PNG-сиквенс на `gl=angle` при c=1 и c=2 | если mp4 разойдутся — виновата растеризация или энкодер |

Блоки G–I добавлены по ходу: их не было в плане, но после результата блока C вопрос
«а как ведёт себя второй бэкенд» стал главным (см. `results/findings.md §2`).
Блоки J–L сняты позже остальных, отдельным заходом: они закрывают долг `findings.md §4`
«`angle` при c=1/c=2» перед решением владельца по `gl`. Блоки A–I к тому моменту были уже
сняты, поэтому J–L живут в своём файле, а не дописываются в `determinism.json`
(та же причина, что у блоков F и G, — `decisions.md` п. 17 и 22).

Разделение C и D — прямое требование RT-01 §5.3 п.1: без него любое расхождение спишут на Chrome,
потому что про энкодер нет даже `UNKNOWN`. Вердикт в каждом блоке формулируется как «совпало» или
«разошлось на кадре N».

## 4. Пороги отката из ADR-0008, применяемые к этим числам

Из `docs/adr/0008-renderer-boundary.md`, раздел «Бюджет AC2». Пороги записаны **до** спайка —
именно поэтому результат интерпретируем. Сравнивается **профиль `final`, 1080×1920, колонка
«кадров/с» (фаза рендера)**:

| измерено | решение по ADR-0008 |
|---|---|
| **≥ 4 кадра/с** | бюджет есть с запасом ×2 — ничего не меняем |
| 2–4 кадра/с | AC2 выполняется без запаса: включаем `minSegmentDurationFrames`, `framemd5` оставляем только в ночном прогоне |
| 1–2 кадра/с | **откат №1:** `scale` финала 0.75 либо fps 30→25 (обе величины входят в `compileProfile`) |
| 0.5–1 кадр/с | **откат №2:** `--gl=angle` на профиле `final` с явной потерей кросс-прогонного детерминизма; AC4 остаётся на `render.ac4.yaml` |
| < 0.5 кадра/с | **откат №3:** план Б по рендереру |

Дополнительные пороги того же ADR, которые спайк тоже проверяет:

* **`framemd5` каждого сегмента** — «полное декодирование каждого сегмента после рендера»;
  колонка `framemd5` в таблице оверхеда показывает цену. Решение ADR (флаг `--verify-frames` +
  ночной прогон) остаётся в силе, если цена сравнима с временем рендера сегмента.
* **`minSegmentDurationFrames`** — оправдан ровно настолько, насколько велика колонка
  «до первого кадра»: это то, что платится на каждом лишнем разрезе.
* **Закрытый GOP и `concat -c copy`** — блок D пишет раскладку ключевых кадров
  (`keyframes.gopSizes`); если GOP не закрыт, включается `assemblyMode: reencode`.
* **Воспроизводимость бандла** (U3, ADR-0006) — два независимых холодных бандла сравниваются
  побайтово: если они расходятся, `bundleHash` в ключе кэша промахивается на каждой сборке.

## 4а. Прогон от батареи (делается руками)

Этот замер нельзя запустить «просто скриптом»: переключить питание программно невозможно, шнур
выдёргивает человек. Поэтому `battery-run.mjs` сначала **проверяет**, что ноутбук действительно
отключён от сети, и отказывается работать, если нет — замер «от батареи», снятый от сети,
хуже отсутствующего, потому что выглядит как настоящий.

**Что делаю я (руками):**

1. Выдернуть шнур из ноутбука. Больше ничего переключать не нужно: `cpuGovernor` и профиль
   питания не трогаем — меряется то, что происходит на самом деле, а не лабораторный случай.
2. Проверить, что заряд ≥ 40 %. Ниже — скрипт откажется стартовать без `--force`.
3. Запустить:

   ```bash
   cd docs/spikes/sp3
   node battery-run.mjs
   ```

4. Не трогать ноутбук, пока идёт замер: посторонняя нагрузка CPU уже измерена отдельно
   (`extra-cpuload`, 3.85 кадра/с против 6.24), и смешивать её с батареей нельзя — иначе
   разница не приписывается ни одному фактору.
5. Когда скрипт напишет «Можно втыкать шнур обратно» — воткнуть шнур обратно.

**Сколько это займёт:** три прогона `angle/final/c=4` по 20–35 с плюс проверки — **около 2–3 минут**
от старта до итоговой строки. Заряда это стоит единицы процентов; цифра «до/после» пишется по
каждому прогону.

**Что скрипт делает сам:**

| шаг | поведение |
|---|---|
| читает питание | `lib/sysinfo.mjs` → `getPower()` → `/sys/class/power_supply` — **тот же способ, что у `machine.json`**: `acOnline`, `batteryStatus`, `batteryCapacity` |
| ноутбук в сети (`acOnline=true`) | печатает «ОТКЛЮЧИ НОУТБУК ОТ СЕТИ И ЗАПУСТИ СНОВА», выходит с кодом 2, **не рендерит ни кадра** |
| заряд < 40 % | предупреждает, что на три прогона может не хватить, выходит с кодом 4 и просит `--force` |
| прогоны | `angle`/`final`/`concurrency=4`, три раза подряд (`--repeats=` меняет число) |
| сравнение | `sha256` mp4 между тремя прогонами **и** с эталоном от сети `angle-4-final` (`124d8f4129caf855…`), плюс `framemd5` |
| тренд | кадров/с и заряд батареи **до и после каждого** прогона — видно, падает ли скорость по мере разряда |
| шнур воткнули посреди замера | прогон помечается отклонением в `deviations`, а не молча зачисляется в «от батареи» |

**Результат:** `results/raw/angle-battery.json`; раздел «Прогон от батареи» в
[results/summary.md](results/summary.md) появляется сам, строки прогресса дописываются в
[results/PROGRESS.md](results/PROGRESS.md).

**Если что-то пошло не так:**

* «✗ Ноутбук подключён к сети» при выдернутом шнуре — проверить `cat /sys/class/power_supply/AC0/online`;
  ядро иногда обновляет это значение с задержкой в пару секунд.
* Ноутбук уснул посреди прогона — прогон получит `FAILED`, остальные продолжатся; повторить
  замер целиком, оборванный ряд не смешивать с новым.
* Нужно снять при низком заряде осознанно (например, чтобы поймать троттлинг на 15 %):
  `node battery-run.mjs --force`.

## 5. Результат

Числа — [results/summary.md](results/summary.md). Их истолкование с пометками
FACT/INFERENCE/UNKNOWN и перечень вариантов решения для владельца —
[results/findings.md](results/findings.md). Спайк **не меняет** ни один ADR: выбор `gl`,
формулировка AC4 и статусы ADR-0006/0007 остаются за владельцем (`decisions.md` п. 20).

Коротко: профиль `final` попадает в полосу **≥ 4 кадра/с** (порог ADR-0008 «ничего не меняем»)
на обоих бэкендах, а вот детерминизм оказался не там, где его ожидали: `swangle` не
воспроизводится прогон-к-прогону, `angle` даёт побайтово равный mp4 **тринадцать прогонов подряд** —
включая прогоны на занятой машине (блок I), прогоны при `concurrency` 1, 2 и 4 (блоки J–L) и три
прогона **от батареи** и три контрольных от сети. Один и тот же файл `124d8f4129caf855…` во всех
**девятнадцати** прогонах: ни параллелизм, ни загрузка машины, ни температура, ни источник питания
на кадры не влияют.

`out/` можно удалять в любой момент: там только отрендеренные файлы и логи, все числа уже
извлечены в `results/`.

## 6. Что спайк НЕ измерил

* **Поведение по мере разряда батареи.** Сам прогон от батареи **сделан** (`battery-run.mjs`,
  раздел §4а; результат — `results/raw/angle-battery.json`, вывод — `findings.md §2.2`): кадры
  побайтово те же, что от сети, цена в скорости −6.2 % (`mains-control.mjs` разложил разрыв:
  две трети приходились не на батарею). Но заряд за три прогона не сдвинулся со 100 %,
  поэтому вопрос «падает ли скорость по мере разряда» остаётся открытым — его закрывает длинный
  прогон или старт с низкого заряда, а не три коротких на полной батарее.
* **Два набора лимитов кэшей** (`core.md §16`): все прогоны сделаны с лимитами из
  `render.final.yaml` (по 512 МБ). Дефолты Remotion (по половине RAM, `FACT` r2 §7.1) не
  запускались сознательно — на 15 ГиБ это два лимита по 7.5 ГиБ при уже измеренном пике 2.5 ГБ.
* **Многосегментная сборка и шов** (`concat -c copy` двух настоящих сегментов): спайк меряет
  один сегмент и стоимость стартов, из которых цена шва выводится арифметикой, но сам шов не
  собирался.
* **Long-form**: ADR-0008 отдельно оговаривает, что для 10–20 минут бюджеты другие.

Каждый пункт — записанный долг, а не забытый; полный список с приоритетами —
в [results/findings.md §4](results/findings.md).
