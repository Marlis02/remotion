# SP-1 — Эргономика формата: спайк не выполнен, решение принято по рассуждению

* **Статус:** закрыт решением владельца, 2026-08-20.
* **Что решал:** ADR-0002 (`proposed`) — разделение «проза `source/*.md`» и «режиссура `direction/*.yaml`» против inline-параметров в тексте.
* **Исходный план спайка:** написать 3 сценария AC1 обоими способами, замерить время написания и время внесения 5 типовых правок (core.md §16, SP-1).
* **Почему не выполнялся:** предпосылка спайка отпала. Он измерял **ручную** эргономику письма, а сценарии и режиссура в этом проекте пишутся LLM через чат; роль владельца — идеи, референсы и точечные указания («поменяй эффект на третьей картинке»).

---

## Решение

**ADR-0002 принят.** Формат: проза `source/*.md` (4 беспараметрических маркера, цифры запрещены) + режиссура `direction/*.yaml` (вся параметрика, ссылки только на якоря `b:`/`sc:`/`ch:`/`r:`).

Статус ADR-0002 меняется с `proposed` на **`accepted (by reasoning, not measurement)`**. Формулировка намеренно отличается от обычного `accepted`: решение не подкреплено измерением, и это должно быть видно в самом статусе.

## Обоснование (три аргумента, все — INFERENCE)

1. **Точечность правок LLM.** Указание «поменяй наезд на третьей картинке» при раздельных файлах превращается в правку двух полей одной записи YAML; проза не открывается вовсе. При inline-формате та же правка означает переписывание строки прозы — и модель может «заодно» изменить формулировку. Класс дефекта «попросил про эффект — получил другой текст» устраняется структурно, а не аккуратностью промпта.
2. **Два потока правок не конфликтуют.** Проза генерируется одним запросом, параметры крутятся другим, часто в разное время. Это буквально два писателя в одни данные. Разделение файлов делает конфликт невозможным механически — ровно та причина, по которой ADR-0002 был написан (D2, дефект 3), только в этом проекте она проявляется не изредка, а постоянно.
3. **Надёжность генерации.** LLM устойчиво заполняет структурированный YAML под известной схемой и неустойчиво — самодельный inline-синтаксис (`[img: harbour zoom=1.12 pan=top-left]`): плавают кавычки, запятые, вложенность. Каждая такая ошибка — сломанная сборка. Тезис D2 «параметры в скобках — это де-факто DSL» здесь подтверждается с другой стороны: генератору такого языка тоже нужна грамматика, которой нет.

## Признак ошибки решения (за чем следить)

Если при работе через чат начнут регулярно возникать ситуации, где хочется сказать «вставь параметр прямо в текст, так короче», — решение пересматривать. Формальный порог: **≥ 3 таких случая подряд на разных роликах**. Честный откат в этом случае — не «немного синтаксиса в прозе», а альтернатива A1 из D2: inline-параметры с настоящим EBNF, `syntaxVersion` и golden-тестами на сообщения об ошибках. Промежуточное состояние остаётся недопустимым.

## Следствие: M2 повышается в приоритете

Находка RT-01 **M2** («LLM-переписывание абзаца уничтожает якоря режиссуры») при таком режиме работы становится не редким, а **штатным** событием: каждый запрос «перепиши середину» потенциально сносит `[beat: …]` вместе со старым текстом, оставляя direction-записи сиротами.

Поэтому механизм, записанный в ADR-0004 «Риски» как «реализуется при первом реальном цикле с LLM-драфтом», переводится в **обязательные для MVP**:

* подача LLM прозы **без маркеров** + обратная вклейка маркеров по span-map;
* `vpe check` печатает исчезнувшие `b:`-якоря с контекстом ±5 слов **до** коммита, а не при сборке.

Это единственное изменение объёма MVP, вытекающее из настоящего решения.

## Приложение: YAML как форма записи (зафиксировано здесь, чтобы не всплывало снова)

Вопрос «почему YAML, а не JSON» закрыт правилом D5: **человекоправимое — YAML, машинописное — JSON/JSONL.** Комментарии в `direction/*.yaml` несут половину смысла файла и в JSON невыразимы.

Известные ловушки YAML и их закрытие:


| Ловушка                        | Пример   | Чем закрыта                                                            |
| ------------------------------------- | -------------- | -------------------------------------------------------------------------------- |
| Норвежская проблема | `no`→`false`  | парсер YAML 1.2 + zod-схема                                           |
| Потеря нуля в числах | `1.20`→`1.2`  | значения-идентификаторы пишутся в кавычках |
| Ведущий ноль               | `08`           | YAML 1.2 + схема                                                            |
| Время как секунды      | `04:30`→`270` | времени в YAML нет: единица — сэмплы (T1)               |
| Табуляция                    | —             | `vpe fmt --check`                                                                |

**Правило:** YAML — только форма записи; правда — в zod-схеме сразу после парсинга. Требуется тест «ядовитых значений» (`no`, `08`, `1.20`, `04:30`, `~`, пустая строка) → типы обязаны совпасть со схемой. Запись добавляется в `docs/invariants.md`.
