## Context

«Провайдер за интерфейсом, получили аудио и тайминги, пошли дальше» невозможно, потому что:

* `FACT` (r1 §2.1) у `eleven_v3` alignment **вырождается**: доля уникальных таймстемпов падает
  до 1–3 % после ~250 символов / ~15 с реплики (измеренная картина по сегментам:
  100 % → 1 % → 3 % → 12 % → 28 %); баг открыт с 2025-12 и не закрыт на 2026-07. Официальный
  воркэраунд самого вендора — прогнать аудио через forced alignment.
* `FACT` (r1 §1.3) оба поля alignment **nullable** — могут не прийти вовсе.
* `FACT` (r1 §1.4) нормализатор переписывает текст, маппинг original↔normalized API не отдаёт;
  SSML `<break>` в normalized-выдаче схлопывается в `.`, `<phoneme>` разворачивается в arpabet.
* `FACT` (r1 §2.3) «Determinism is not guaranteed» даже при фиксированном seed.
* `FACT` (r1 §3.1) стичинг-хендлы живут 2 часа, требуют полного завершения предыдущего запроса
  и несовместимы с `enable_logging=false`.
* `FACT` (r1 §5.1) половина альтернативных провайдеров не даёт пословных таймкодов вовсе
  (Google — только SSML-марки), а у Polly speech marks и аудио — **два разных вызова**.

Итог без защиты: вырожденный alignment попадает в коммитимый артефакт **молча**, все субтитры
чанка вспыхивают одновременно, AC5 нарушен на секунды, и **ни один тест не падает** — AC4
сравнивает кадры двух одинаково неправильных рендеров.

## Decision

**1. Приёмка дубля на границе провайдера — до записи в артефакт.**

```ts
interface TakeHealth {
  readonly charIdentity: boolean;      // characters.join('') === отправленный spoken-текст
  readonly lengthsMatch: boolean;      // три массива одной длины
  readonly monotonic: boolean;         // start неубывает, start[i] <= end[i]
  readonly uniqueTimestampRatio: number;
  readonly maxEqualRun: number;        // самая длинная серия символов с одинаковым временем
  readonly tailResidualSamples: number;// end[last] против numSamples фактического PCM
  readonly verdict: 'accepted' | 'rejected';
  readonly rejectReason?: string;
}
```

Провал — **не WARN**, а отказ принять дубль. Лестница реакции (исправлено по M12):
`ретрай ×N` (N — константа профиля, кандидат 2; тот же запрос, потому что `FACT` r1 §2.3
детерминизм не гарантирован и второй ответ может быть здоровым) → **падение сборки** с
сообщением вида «чанк `<chunkKey>` не прошёл приёмку (`uniqueRatio 0.03`, `maxEqualRun 180`):
сократи абзац, поставь `[pause:]` на границе предложения или включи `bind: forced-alignment`
в профиле».

**Чего лестница делать не имеет права: делить чанк.** В первой редакции провал приёмки вызывал
автоматическое деление, а деление меняет `chunkKey` и ключи `voice`. Тогда границы чанков
становились функцией недетерминированного ответа сети, следующий прогон давал **другое**
разбиение, кэш промахивался без изменения входов, и деньги тратились повторно — то есть §3
(«множество границ зависит только от байтов абзаца») нарушался первым же срабатыванием
аварийной лестницы из §1. Два правила одного ADR противоречили друг другу; побеждает §3,
потому что на нём стоит предсказуемость стоимости правки.
Решение о делении принимает человек и записывает его **в текст** (`[pause:]` на границе
предложения) либо **в профиль** (`maxChunkChars`) — в обоих случаях границы остаются функцией
зафиксированных байтов, а не события.
`charIdentity` превращает `UNKNOWN` (r1 §1.4: гарантия `join('') === input` нигде не
декларирована) в проверяемый инвариант. Метрики пишутся в дубль — это же даёт объективный
критерий выбора при A/B.

*Дополнено: SP-2, блоки findings U4.1 и SP-2b.2 (2026-08-21).* Измерение меняет **класс** этой
проверки, но не её судьбу. `FACT`: тождество выполняется **56 раз из 56** — 28 строк на
`Daniel — Steady Broadcaster` (`premade`) и те же 28 на `Michael C. Vincent` (`professional`), —
включая все ловушки F1–F16 из §10 и все девять числовых классов; на длинных чанках оно тоже
держится (202 / 403 / 810 / 1514 символов на Daniel, **2689** code points на Michael). Значит
`charIdentity` — не защита от вероятного события, а **дешёвый ассерт на редкое**. `INFERENCE`:
это **не** довод его убрать — гарантия по-прежнему нигде не декларирована (`FACT` r1 §1.4), а
цена проверки равна одному сравнению строк. Измерено на **двух** голосах и **одной** модели
(`eleven_multilingual_v2`); на другие модели не переносится.

**Рабочая точка и пороги приёмки** (`FACT`, findings U6 + SP-2b.5). На здоровом материале
`uniqueTimestampRatio` = **1.000**, `maxEqualRun` = **1**, и так на всех проверенных ступенях —
202 → 403 → 810 → 1514 → **2689 code points / 155.4 с**. Картина деградации из `FACT` (r1 §2.1)
на `eleven_multilingual_v2` **не воспроизводится**: issue #707 и #760 заведены на `eleven_v3` и
`text-to-dialogue`, то есть решение «не брать v3, пока #707 открыт» подтверждено измерением, а не
просто сохранено. Следствия для порогов:

* порог `uniqueTimestampRatio ≥ 0.9` **остаётся как есть**: он лежит далеко от рабочей точки и
  сработает только на настоящей патологии, то есть ложных срабатываний не даст;
* порог-кандидат `maxEqualRun ≤ 8` безопасен, **но агрессивный порог 2 брать нельзя** — он
  сломал бы приёмку на любом абзаце с эмодзи. `FACT`: единственные строки с `ratio < 1` — строки
  с эмодзи (`🚢` → 0.976 при `maxEqualRun` 2; `👍🏽` → 0.956 при 3), потому что непроизносимые
  code points получают интервал **нулевой длины** и делят старт с соседом. Эмодзи в прозе линтом
  ADR-0002 §3 не запрещены, то есть случай достижим;
* отсюда обязательное следствие для §5: токен, состоящий только из непроизносимых символов,
  обязан получать `status: 'absent'`, а **не** интервал `[t, t]`, — иначе субтитр получит слово
  нулевой длительности и это пройдёт мимо всех проверок.

**`UNKNOWN`, который спайк не снял:** поведение при `alignment: null` (оба поля nullable, `FACT`
r1 §1.3) за 49 успешных вызовов не наблюдалось ни разу. Это не значит, что `null` не приходит:
приёмка обязана его обрабатывать, и в `tts:mock@1` соответствующий тест написан.

**2. Дубль самоописателен.** `voice/takes/<chunkKey>.json`:

```
{ chunkKey, spokenText, normalizerVersion, sourceHash,
  pcm: { sha256, numSamples, sampleRate }, leadInSamples, tailSamples,
  health: TakeHealth,
  provenance: { providerId, modelId, voiceId, voiceCategory, seed, requestId, billedUnits,
                planTierAtGeneration, generatedAt, conditionedOn: [chunkKey] },
  bindings: [ { anchorId, startSample, endSample, status, confidence } ] }
```

Ключевое: **фактически отправленный spoken-текст и готовые привязки лежат рядом с дублём.**
Тогда пересчёт привязок из старого дубля не требует старого нормализатора вовсе, расхождение
«текст дубля ≠ текущий spoken-текст» становится явным условием инвалидации, а AC6 выполняется
даже без доступа к байтам. `planTierAtGeneration` обязателен: `FACT` (r3 §3.2) коммерческие
права на аудио даёт только платный план, и тариф на дату генерации ретроспективно не восстановить.

*Дополнено: SP-2, блоки voice-and-tier §5 п.1, findings «Тарификация и учёт» и SP-2b.7
(2026-08-21).*

**`voiceCategory` — новое поле** рядом с `voiceId`. `FACT`: класс голоса (`premade` /
`professional` / клонированный) определяет, доступен ли голос через API на данном тарифе —
библиотечный голос на Free через API отвечает `HTTP 402 paid_plan_required`, списывая 0. Без
этого поля «дубль снят премейдом» и «дубль снят боевым голосом» задним числом различаются только
по дате. `voiceCategory` — часть provenance («как сделано»), а **не** часть `voiceKey`
(ADR-0006 §2): она выводится из `voiceId` и не является независимым входом идентичности.

**`billedUnits` — не длина строки.** `FACT` (SP-2): единица тарификации — **code points**
отправленного `spokenChunkText`, а не UTF-16 units и не графемы (две строки с эмодзи различают
счётчики: 668 против 670 на блоке 1). `FACT` (SP-2b.7): но **число** списанных единиц
тарифо-зависимо — на Free списывалось `1.00 × code points` (5222 = 5222), на Creator списывается
`round(codePoints × 0.55)` **покалльно, с округлением по каждому запросу** (4122 отправлено →
2268 списано; `floor`, `ceil` и округление от суммы блока отсеяны на трёх независимых окнах).
Отсюда правила заполнения:

* `billedUnits` = **«сколько единиц отправлено провайдеру»** — число code points
  `spokenChunkText`. Это вычислимо офлайн и проверяемо тестом; форма данных не меняется;
* ставка (множитель тарифа) хранится **рядом с уже существующим `planTierAtGeneration`**, а не
  внутри `billedUnits`. «Сколько отправлено» и «сколько стоило» — две разные величины, случайно
  склеенные в одно имя;
* множитель **не зашивается константой в код**: `UNKNOWN` (SP-2b.7) — откуда берётся 0.55, в
  ответах API нет (`token_cost_factor` модели равен 1 в обоих снимках аккаунта), и стабильность
  множителя во времени и по моделям не измерялась. Его место — снимок аккаунта, с пересчётом при
  расхождении;
* источник сверки — **`GET /v1/usage/character-stats`** по временному окну, а **не** дельта
  `character_count` вокруг запроса: `FACT` (SP-2) подписка обновляет `character_count` с
  задержкой **20–40 секунд**, и дельта, снятая вокруг вызова, читается как **0**. Поштучная
  сверка через `GET /v1/history` в нашем аккаунте недоступна (право `speech_history_read`).

**3a. `chunkKey` — идентичность места; `voiceKey` — идентичность содержимого (C2).**

`chunkKey` использовался как имя take-файла, как элемент `conditionedOn` и как объект
собственного теста §3, но **не был определён ни в одном документе** (10 употреблений, 0
определений). Оба естественных варианта сломаны: позиционный переименовывает все последующие
take-файлы при вставке абзаца, контентный схлопывает два одинаковых абзаца (повторяющаяся
концовка, рефрен) в один файл, у которого `conditionedOn` верен максимум для одного места.
Определение:

```
chunkKey = base32( blake3( chapterId ‖ sceneId ‖ paragraphOrdinalInScene ‖ splitIndex
                           ‖ blake3(spokenChunkText) ) )[:16]

voiceKey = blake3( spokenChunkText, providerId, modelId, voiceId, seed, providerOpts,
                   roleDigest, ttsPipelineVersion )          // = ключ кэша voice, ADR-0006 §2
```

*Изменено: RM1, решение владельца 1, 2026-08-22 — в `voiceKey` добавлен `roleDigest`.*

Разделение двух понятий, которые в первой редакции были склеены, разрешает конфликт целиком:

| Свойство | Обеспечено чем |
|---|---|
| правка слова меняет ровно один `chunkKey` | `spokenChunkText` в хэше |
| правка в **другой** сцене/абзаце не трогает наш `chunkKey` | адрес локален: `ordinal` **внутри сцены**, сквозного счётчика по документу нет |
| два одинаковых абзаца в разных местах различимы | `chapterId ‖ sceneId ‖ ordinal` в хэше |
| два одинаковых абзаца **не оплачиваются дважды** | `voiceKey` от них совпадает ⇒ попадание в кэш `voice`, один blob PCM в `.store`, два take-файла ссылаются на один `pcm.sha256` |
| `conditionedOn` верен для каждого места отдельно | `conditionedOn` живёт в take-файле, а take-файл — на место, а не на текст |

`splitIndex` — порядковый номер части при структурном делении длинного абзаца (§3); при делении
`whole` он равен 0.
Следствие для git: правка слова **переименовывает** один take-файл (появляется новый, старый
остаётся). Старые take-файлы не удаляются: они по 3–5 КБ, дают историю и откат, а PCM в `.store`
всё равно не подлежит GC. Уборка (`vpe voice gc`) — не v1.
Это делает избыточным отдельный слой `takeChoice` (раскрой 2.1 п.2): выбор другого дубля в v1 —
это `--force` плюс git-история, а не третий адресный слой.

**3a-bis. Пресеты ролей голоса: где они лежат и как сцена на них ссылается.**
*(Добавлено: RM1, решение владельца 1, 2026-08-22 — вариант «б» вопроса `docs/roadmap.md` §8 №1;
закрывает пометку Charter §6 «Открыто и адресовано RM1».)*

Задача была: выразить «основной диктор / цитата / вставка» и смену темпа между сценами, не
подставляя голый `voice_id` в ролик. Выбрано **отдельное семейство**, а не поле в направлении
и не роль на весь ролик:

* **где живут пресеты:** `voice/roles.yaml`, `schema: voice-roles/1` (раскладка —
  [ADR-0005](0005-project-format.md) §1, §1b). Роль несёт `voice_settings` и модель/голос
  **по умолчанию для роли**. `voice_id` в файл не попадает — в роли лежит **имя переменной
  окружения**, значение берётся только из `process.env` (CLAUDE.md §2);
* **как сцена ссылается:** записью `direction/NN-name.yaml` с `track: voice`:

```yaml
  - recordId: "…"                                  # 4 случайных байта, как у любой записи
    at: { kind: anchor, anchor: "sc:turn" }        # scope-якорь сцены
    until: { kind: anchor, anchor: "ch:main" }     # необязательно; по умолчанию — конец scope
    track: voice
    voiceRole: "narrator"                          # вместо template/params
```

Почему именно так, а не «поле сцены»: сцена объявляется в `source/*.md` маркером `## scene:`,
а **параметрика в прозе запрещена** (ADR-0002) — поле потребовало бы либо нового маркера сверх
нормативной таблицы ADR-0002 §2 (это отдельный ADR), либо второго механизма адресации в
`direction/1` рядом с `records[]`. Форма записи режиссуры уже есть, и она уже адресует сцену
через `sc:`-якорь.

**Что при этом не ломается — проверено по двум правилам поимённо:**

* **A1** («ни один override и ни одна direction-запись не ссылаются на `w:`»): запись адресует
  `sc:`-якорь. Ссылок на `w:` в ней нет и быть не может — тест A1 (греп на подстроку `w:` в
  `direction/**`) остаётся зелёным без единой оговорки;
* **V3** («границы и `chunkKey` = f(байты абзаца, структурный адрес)»): роль **не входит в
  `chunkKey`** ни одним полем и **не меняет границ чанков**. Формальный инвариант §3 остаётся
  верным дословно. Роль влияет только на **содержимое** дубля и потому входит в `voiceKey` —
  через `roleDigest` (ADR-0006 §2), обязательный в `cacheKeyView` стадии `voice`.

**Цена, записанная явно.** [ADR-0001](0001-domain-model.md) перечисляет `Track` как
`speech·music·sfx·caption·visual·effect`; `voice` становится **седьмым** именем и при этом
**директивным**: запись с `track: voice` не порождает клип Timeline, а питает **SpeechPlan**
(стадия `plan`, задача `V-03`). Это отличает её от `speech` — дорожки Timeline, на которой лежат
клипы PCM. Смешивать два имени нельзя, и поэтому взято новое, а не перегружено существующее.
Вторая часть цены — **+1 семейство файлов и +1 будущая миграция** (V7); она принята сознательно
ради того, что роль задаётся один раз на канал и переиспользуется между роликами.

**3. Границы чанков — только структурные.**
Чанк = **абзац**. Если абзац превышает безопасный предел (из SP-2), он рекурсивно делится по
границам предложений **внутри себя**, слева направо.
*Дополнено: SP-2, findings U6 + SP-2b.5 (2026-08-21).* `FACT`: безопасный предел **не найден** —
`uniqueTimestampRatio` не отклонился от 1.000 ни на одной ступени вплоть до **2689 code points /
155.4 с**, то есть окрестность порога issue #707 (2674 симв. / 60 с) пройдена без следа
деградации и с превышением по длительности в 2.6 раза. `INFERENCE`: **предел деления абзаца
упирается не в качество alignment.** Поле `maxChunkChars` в профиле остаётся, но его значение
выбирается из других соображений — просодия, стоимость перегенерации, гранулярность AC3.
`UNKNOWN`: поведение при **многократных** длинных запросах подряд (issue #760 описывал деградацию
как функцию суммарной длительности сессии) — один длинный запрос не то же самое, что десять.
**Формальный инвариант: множество границ чанков абзаца P зависит только от байтов P.**
Никакого бегущего счётчика символов по документу — иначе вставка одного слова в начале сцены
сдвигает все последующие границы, меняет все последующие `chunkKey` и вызывает **платную
перегенерацию всего остатка проекта**. Это прямое столкновение двух требований research
(качество alignment хочет коротких кусков фиксированного размера; AC3 и бюджет хотят границ,
инвариантных к правкам выше по тексту), и оно разрешается в пользу структуры.
**Формулировка инварианта уточнена (C2):** границы и идентичность чанка зависят только от
**байтов абзаца и его структурного адреса** — «только от байтов P» было неверно, потому что
собственным тестом §3 выбирало контентный вариант `chunkKey`, который схлопывает одинаковые
абзацы.
Тест: вставить слово в первый абзац фикстуры — множество `chunkKey` обязано измениться ровно
для одного чанка; вставить **абзац целиком** в сцену 1 — `chunkKey` абзацев сцены 2 обязаны
остаться прежними, а внутри сцены 1 измениться у всех, стоящих ниже вставки (это честная цена
локального счётчика и она не стоит денег: `voiceKey` их не меняется, кэш `voice` попадает).

**4. Стичинг — только текстом.** `previous_text` / `next_text`, **никогда `previous_request_ids`**:
хендлы недетерминированы, живут 2 часа и образуют транзитивную цепочку ключей кэша (ADR-0006).
Дубль записывает `conditionedOn`; сборка предупреждает при несогласованной истории сшивки у
соседей — это единственный дешёвый детектор просодического шва.

*Дополнено: SP-2, блок findings U5 (2026-08-21).* `FACT`: `previous_text`/`next_text`
**не тарифицируются** — 264 символа контекста не попали в списание. Довод «контекст стоит денег»
исключается из рассмотрения целиком; остаётся только довод про ключ кэша (ADR-0006 §2), и он не
про деньги. `FACT`: контекст **влияет на звук** — PCM отдельного предложения не совпал с версией
без контекста ни разу из трёх, длительность отличается до 139.3 мс (3.06 %). `FACT`: суммарная
длительность склейки против одного запроса — **−232 мс** с контекстом и **−464 мс** без него
(эталон 15.093 с). `INFERENCE`: передача соседних предложений возвращает **примерно половину**
того, что теряется при разбиении, — то есть решение «стичинг только текстом» имеет измеримое
основание, а не только отрицательное («не брать `request_ids`»).
`UNKNOWN` **по построению**: слышна ли разница на шве. Это вопрос к ушам владельца; файлы
подготовлены (`out/b5-{a,b,c}.wav`, швы на 4.690/10.263 с и 4.551/10.124 с) — **на Daniel**, на
боевом голосе блок 5 не переснимался (долг 9). До ответа fallback-ключ ADR-0006 §2 (хэш смежного
предложения в ключе `voice`) остаётся не принятым, а `conditionedOn` — диагностическим полем.

**5. Стадия `bind` — явная точка расширения** между дублём и Timeline:

  readonly requiresNetwork: boolean;

Дефолт v1 — `provider-timestamps` (дешевле). Интерфейс и стадия кэша закладываются сразу: `FACT`

**7a. Словари произношения в v1 не используются вовсе (C1). `Lexicon` удалён из модели.**

Первая редакция держала `lexicon.yaml` как рукоправимый артефакт и как штатный способ поправить
произношение имени (ADR-0004, класс правок 8). Две независимые дыры:

1. **Дыра в ключе.** Ключ стадии `voice` — литеральный список полей (`cacheKeyView`, ADR-0006 §6),
   и `lexicon` в нём отсутствовал. Правка словаря меняет **звук**, не меняя ключ ⇒ автор правит
   произношение, слышит старое аудио и думает, что словарь не работает. Это ровно класс «валидный
   по ключу, но неверный оплаченный артефакт», против которого написаны `cacheKeyView`, матрица
   мутации и приёмка дубля, — и он проходил мимо всех трёх, потому что ни один список его не
   содержал.
2. **Дыра в приёмке.** `FACT` (r1 §1.4): словари поддерживают не только `<phoneme>`, но и
   **alias**-правила («UN» → «United Nations»), а alias меняет длину нормализованного текста
   ровно так же, как нормализатор чисел. Приёмка (§1) требует
   `characters.join('') === отправленный spoken-текст`; при включённом alias это тождество
   **обязано** нарушиться ⇒ штатное действие («поправить произношение имени») превращается в
   срабатывание аварийной лестницы: отказ приёмки → ретрай → падение сборки. Исправление одной
   буквы в словаре ломает чанк и тратит деньги.

**Решение (fallback из C1, устраняющий класс целиком):** `pronunciation_dictionary_locators` в v1
**не используются**; поле `lexicon.yaml` удалено из раскладки (ADR-0005), сущность `Lexicon` —
из модели (ADR-0001), класс правок 8 переехал на `source`. Произношение выражается **уже
существующим** механизмом:

```
[say: Worcestershire | WUUS-ter-sher]
```
*Изменено: язык контента → en, Charter rev3. Было `[say: Мосгортранс | Мос-гор-транс]`.
Английский даёт тот же класс: имена и топонимы, читаемые не по написанию
(`Worcestershire`, `Leicester`, `Thames`, `Arkansas`).*

Он живёт в исходнике ⇒ входит в `spokenChunkText` ⇒ попадает в `voiceKey` **по построению**,
сохраняет `charIdentity`, не требует ни нового поля в ключе, ни новой сущности, ни нового файла.
Цена: произношение задаётся в каждом месте употребления, а не один раз на проект. Для роликов на
150 слов это единицы вхождений; при первом же проекте, где это станет больно, словарь возвращается
**вместе с** обязательным `lexiconDigest` (blake3 канонической формы **только применимых к этому
чанку** записей) в `cacheKeyView` стадии `voice`, покрытием матрицей мутации и записью применённых
записей в provenance дубля — иначе он не возвращается. Alias-правила запрещены и тогда: alias — это
второй, неявный нормализатор, а весь ADR-0002 построен на том, что нормализатора нет.

**Что при этом остаётся измеряемым:** SP-2 всё равно проверяет поведение `charIdentity` при
включённом словаре с alias-правилом. Отрицательный результат подтвердит запрет; положительный —
удешевит будущее возвращение словаря. Отказ от механизма не отменяет измерения.

*Дополнено: SP-2, блоки findings C1 и SP-2b.4 (2026-08-21); решение владельца 5.* `FACT`: замер
**не выполнен ни в SP-2, ни в SP-2b**. `POST /v1/pronunciation-dictionaries/add-from-rules` вернул
**HTTP 401** — у API-ключа нет права `pronunciation_dictionaries_write`; в SP-2b выяснилось, что
нет и `pronunciation_dictionaries_read`. Списано 0, словарь не создавался. Это ограничение
**прав ключа**, а не тарифа: тот же ключ на том же тарифе сделал 34 платных вызова TTS.
`UNKNOWN`: сохраняется ли `charIdentity` при включённом alias-правиле. Запрет alias остаётся
обоснованным **рассуждением** (alias меняет длину нормализованного текста ⇒ тождество обязано
нарушиться), а не измерением. `INFERENCE` — косвенное свидетельство **в пользу** запрета,
усилившееся на двух голосах: `normalized_alignment` совпал у Daniel и Michael **побайтово на
28/28** строк, то есть слой канонизации от голоса не зависит вовсе; если словарь работает на этом
же слое, alias проявится только в `normalized_alignment` и `charIdentity` не сломает, а если
раньше — сломает. Различить две гипотезы без замера нельзя.
**Решение владельца:** словарь остаётся исключённым из v1; долг остаётся открытым, цена досъёмки —
**76 кредитов** и два бесплатных вызова после включения права в дашборде ElevenLabs
([sp2-closure.md](../spikes/sp2-closure.md), долг 1).

**10. Оспариваю V5 в части формулировки.**
V5: «маркеры вырезаются из текста ДО отправки в TTS; нужен алигнер original ↔ normalized».
Предлагаю: «**маркеры подставляются по таблице (tts-текст, caption-текст)**; нужен
нормализатор-**трансдьюсер** с монотонной span-map + `apply_text_normalization: "off"`».
Причины:
* `[say: 23% | twenty-three percent]` подставляет **разное** в речь и в субтитр — вырезанием
  это не выражается, а без него субтитр `twenty-three percent` вместо `23%` неизбежен
  *(пример переведён: язык контента → en, Charter rev3; было `[say: 23% | двадцать три процента]`)*;
* `[emph]` не может влиять на речь, **не изменив строку**: `FACT` (r1 §2.2) у v2/flash
  единственный документированный механизм — SSML `<break>`, у v3 — только аудио-теги,
  многоточия и капитализация; `FACT` (r1 §1.5) SSML внутри чанка с точными якорями использовать
  нельзя. Поэтому в v1 объявляется вслух: **`[emph]` — чисто визуальный маркер, голосовая эмфаза
  не поддерживается**; если она когда-нибудь понадобится, она входит через тот же механизм, что
  `[say:]`, и обязана иметь span-map со **вставками**, а не только с удалениями;
* fuzzy-алигнер original↔normalized остаётся только как fallback для провайдеров без capability
  отключения нормализации.

**Property-тесты трансдьюсера** (сильнее любого набора примеров): тотальность (каждый байт
spoken-текста имеет прообраз в исходнике либо помечен вставленным); монотонность span-map;
round-trip `reconstructDisplay(spoken, spanMap) == display-текст`. Плюс **fuzz-набор ловушек**.

единица индексации названа окончательно: code points.** `FACT`: длина `alignment.characters`
совпала с числом **code points** входа на 28/28 строк каждого из двух голосов; с числом UTF-16
units — на 26, с числом графем — на 26. Гипотезы различают ровно три строки, и все три дают один
ответ: `café` в NFD (45/45/44 → массив 45 ⇒ не графемы), `🚢 ahead` (43/42/42 → 42 ⇒ не UTF-16),
`👍🏽 ok` (47/45/44 → 45 ⇒ ни то, ни другое). Тот же счётчик — единица тарификации (SP-2b.7).
`INFERENCE`: span-map трансдьюсера обязана быть монотонной **в code points**; реализация,
индексирующая spoken-текст через `str[i]` или `str.length`, разъедется с `alignment` на первом же
эмодзи — и разъедется **молча**, потому что `charIdentity` при этом останется истинным. Значит
индексация ведётся по `[...text]` (или по итератору строки), а `Intl.Segmenter` в движке не нужен
вовсе — он дал бы **неверную** единицу; это совпадает с запретом `Intl` из Charter V8.

## Alternatives

| Альтернатива | Почему могла быть лучше | Почему отклонена |
|---|---|---|
| **Доверять таймкодам провайдера без приёмки** | ноль кода | открытый баг вырождения проходит в ролик молча; ни один тест не падает |
| **Forced alignment как единственный источник привязок** | `FACT` (r1 §4.3) MFA ~20 мс средней ошибки — с запасом под 80 мс; capability провайдера перестаёт влиять на корректность | тяжёлая зависимость (conda+Kaldi) или лицензионная мина (`FACT` r1 §4.2: веса MMS_FA — CC-BY-NC, aeneas — AGPL); плюс `FACT` (r1 §4.5) контролёр AC5 обязан быть **другим** алгоритмом — если FA стал источником, контролёра надо искать заново. Принято как **вторая реализация** одного интерфейса |
| **`eleven_v3` как основная модель** (аудио-теги, выразительность) | лучшее качество речи | `FACT` (r1 §2.1) таймкоды сломаны, issue открыт 8 месяцев; стичинг для v3 недоступен. Не брать, пока #707 открыт |
| **Чанк = фиксированные ~200 символов** (воркэраунд из issue) | 100 % уникальных таймстемпов | вставка слова сдвигает все последующие границы ⇒ платная перегенерация остатка проекта; деградацию контекста лечим `previous_text`/`next_text` |
| **Стичинг через `previous_request_ids`** | лучшая просодия на стыке | недетерминированный вход, TTL 2 часа, транзитивный каскад ключей. `UNKNOWN`: слышна ли разница (SP-2); если слышна — fallback из ADR-0006 (хэш смежного предложения) |
| **Хранить только alignment провайдера, привязки считать на лету** | меньше данных в git | без span-map старого нормализатора привязки для старого дубля не восстановить ⇒ AC6 ломается; ~5 КБ на ролик — приемлемая цена самоописательности |

## Consequences

**Положительные**

* Приёмка (~30 строк) — единственная защита от того, что открытый баг провайдера пройдёт в ролик
  молча.
* `chunkKey`/`voiceKey` разведены ⇒ повторяющаяся концовка канала («подпишись») стоит денег
  **один раз**, а `conditionedOn` и health-метрики остаются верными для каждого места.
* Отказ от словарей произношения убирает одну сущность, один файл, один рукоправимый артефакт и
  единственную дыру в ключе `voice`.
* Самоописательный дубль делает AC6 выполнимым для аудио и делает миграции нормализатора
  безопасными.
* Структурные границы чанков делают стоимость правки предсказуемой и проверяемой тестом.
* Mock-провайдер делает весь тестовый контур бесплатным, герметичным и детерминированным.

**Отрицательные**

* Приёмка может отвергнуть дубль, который «на слух нормальный», и потратить деньги на ретрай;
  пороги настраиваемы и лежат в `audioProfile`.
* Отказ от `request_ids` может стоить качества просодии на стыках (`UNKNOWN`, SP-2).
* Голосовая эмфаза в v1 отсутствует — это ограничение продукта, и о нём сказано вслух.
* Произношение имени задаётся в каждом месте употребления (`[say:]`), а не один раз на проект.
* Провал приёмки после `N` ретраев **останавливает сборку** и требует решения человека. Это дороже
  по вниманию, чем автоматическое деление, и дешевле по деньгам и по предсказуемости.

**Риски**

* **Риск снят: не реализовался** *(изменено: SP-2, блоки findings U4.1 и SP-2b.2, 2026-08-21).*
  Прежняя формулировка зачёркнута целиком (внутреннее зачёркивание «~~на русском~~ → на
  английском» было внесено Charter rev3 и сохраняется как часть истории):

  > ~~Если SP-2 покажет, что `charIdentity` не выполняется на английском даже при
  > `apply_text_normalization: "off"`, придётся либо ужесточать линт ADR-0002, либо включать
  > fuzzy-алигнер по умолчанию. Оба пути известны заранее. (Изменено: язык контента → en,
  > Charter rev3. Априорная вероятность провала ниже: `FACT` (r1 §1.4) нормализатор ElevenLabs
  > англоцентричен, то есть на английском его поведение документировано лучше всего. Но
  > `UNKNOWN` не снимается рассуждением — SP-2 остаётся блокирующим.)~~

  `FACT`: тождество выполняется 56/56 на двух голосах при `apply_text_normalization: "off"`.
  `INFERENCE`: ужесточать линт по этой причине не нужно, и **fuzzy-алигнер original↔normalized
  для ElevenLabs в v1 не нужен ни как дефолт, ни как включаемая опция** — он остаётся только тем,
  чем объявлен в §10: fallback для провайдеров без capability отключения нормализации.
  Оговорка, без которой вывод был бы шире измерения: `off` гасит нормализатор чисел, дат, денег и
  сокращений, но **не** второй слой — канонизацию типографики и удаление непроизносимых символов
  (`’→'`, `—→--`, `–→-`, `“”→"`, `…→...`, NBSP→пробел, эмодзи удаляются). Этот слой виден
  **только** в `normalized_alignment`, а привязки строятся по `alignment`, поэтому для движка он
  безопасен; `normalized_alignment` проекту не нужен вовсе и не должен попадать ни в дубль, ни в
  приёмку.
* `[say:]` как носитель произношения меняет **и субтитр**: левая часть идёт в caption. Для имени
  это обычно и нужно (`Worcestershire` в субтитре — *пример переведён: язык контента → en,
  Charter rev3*), но случай «в субтитре одно, в речи другое, и оба
  отличаются от исходной формы» выражается только через ту же пару. Если SP-2 покажет, что таких
  случаев много, словарь возвращается на условиях, записанных в §7a.
* Если безопасный предел длины чанка окажется жёстче абзаца, деление пойдёт по предложениям —
  и тогда качество просодии придётся компенсировать `previous_text`/`next_text`, что уже заложено.
