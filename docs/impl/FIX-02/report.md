**Дата:** 2026-09-11. **Машина:** ноут владельца, `engineFingerprint 3217a4cf…` (эталон).
**Вход:** долг №265 ([`DEMO-POMPEII`](../DEMO-POMPEII/report.md) §3), задание владельца
`IMPL-NIGHT-02` часть 1. **Денег и сети:** ноль.

**Одной строкой.** Черновой профиль показывал не тот кадр не потому, что масштаб раскрывался
дважды, а потому, что он не раскрывался НИ РАЗУ: рендерер уменьшает вьюпорт и обрезает

измерением, вторая — уже по дороге к `VID-02a`, и она стоила одной ложной правки.

**Читается это однозначно.** Кадр 540×960, содержимое в масштабе 1:1, видна левая верхняя
четверть композиции. То есть **рендерер уменьшает ВЬЮПОРТ и не уменьшает СОДЕРЖИМОЕ**.
Утверждения «рендерер раскрывает `scale` сам» не существует как факта — и значит вторая
половина диагноза №182 («масштаб дважды: рендерер И мы») была **неверна**. Первая половина
верна: до `FIX-01` композиция авторилась в масштабированной геометрии (`#root` и `.layer` =
`width × height`) и вдобавок жалась трансформой, что и давало 270×480 из 540×960 — измеренные
тогда `100 / 0 / 0 / 0`. `FIX-01` снял ОДНУ половину из двух, и множитель стал 1 там, где нужен
0.5.

**Почему это не заметили двенадцать дней.** Прибор `FIX-01` мерил долю НЕЧЁРНЫХ пикселей по
квадрантам, а она равна `100/100/100/100` и у верного кадра, и у кадра из четверти композиции,
растянутой на весь кадр. Опыт «Б», на котором стояло решение «какая из двух простановок
лишняя», отвечал на различающий вопрос одним и тем же числом.

## 2. Почему масштаб нельзя было поставить на `#root` (это тоже измерение, а не выбор)

План §1.3 предполагал `#root { transform: scale(s); transform-origin: 0 0 }`. Проба показала
другое:

| куда поставлен масштаб | `scale: 0.5`: ЛВ-маркер | занятая часть кадра 540×960 |
|---|---|---|
| нигде (дерево до правки) | `0,0` **100×100** | `0,0…539,959`, но это ЧЕТВЕРТЬ композиции |
| `#root { transform: scale(0.5) }` | `0,0` 50×50 | **`0,0…269,479`** — четверть кадра |
| `#root { zoom: 0.5 }` | `0,0` 50×50 | **`0,0…269,479`** — та же четверть |
| **`.layer { transform: scale(0.5) }`** | **`0,0` 50×50** | **`0,0…539,959` — весь кадр** |

Контрольный опыт, разделивший «браузер не умеет» и «рендерер мешает»: тот же `index.html`,
снятый прямым скриншотом `chrome-headless-shell --window-size=540,960`, даёт **верный кадр в
обоих вариантах с масштабом на `#root`** — все пять маркеров на местах. Значит дело не в Chrome.

**Причина найдена в вендоре.** Инжектируемый рантайм `hyperframes@0.8.5` на своей инициализации
выполняет (`RUNTIME_IIFE` в `hyperframes/dist/cli.js`):

```
d.style.overflow = "hidden";
g = D(d.getAttribute("data-width"));  h = D(d.getAttribute("data-height"));
g && (d.style.width = g);  h && (d.style.height = h);
```

то есть **перезаписывает размер `#root` ИНЛАЙНОМ на `data-width`/`data-height`** (540×960)
поверх нашей таблицы стилей и ставит корню `overflow: hidden`. Отсюда обе строки таблицы: без
нашего масштаба слои 1080×1920 обрезаются корнем до 540×960 — это и есть №265; с нашим
масштабом на корне обрезка происходит ДО него, и ×0.5 накладывается на уже обрезанное — это и
есть `100/0/0/0` из `FIX-01`.

## 3. Правка — одна строка

[`materialize.ts`](../../../packages/renderer-hyperframes/src/materialize.ts), функция
`indexHtml`:

```ts
const layerScale = manifest.scale === 1 ? '' : ` zoom: ${String(manifest.scale)};`;
```

и она подставляется в правило слоя:

```
.layer { position: absolute; inset: 0; width: ${baseWidth}px; height: ${baseHeight}px;${layerScale} }
```

Плюс два правила приведены к геометрии ВЫХОДА за когерентность с тем, что вендор всё равно
проставит инлайном (`html, body` и `#root` — `width × height` вместо `baseWidth × baseHeight`);
при `scale === 1` обе строки не отличаются от прежних ни байтом, потому что `width === baseWidth`.

### 3-бис. `zoom`, а не `transform` — вторая находка, и она перевернула первое решение

**ЧТО СТОЯЛО СНАЧАЛА.** `transform: scale(); transform-origin: 0 0` на `.layer`. Довод был
разумный и оказался неполным: `transform` не трогает раскладку, значит `host.offsetWidth`,
которым реализации считают доли кадра, означает на черновике то же, что на полном. На линейке
эта правка давала БЕЗУПРЕЧНЫЕ числа — все пять маркеров с расхождением 0 px.

**ЧТО ЕЁ ОПРОВЕРГЛО.** `kenburns@1` анимирует слой НИЖЕ себя через GSAP (`x`, `y`, `scale`), а
GSAP пишет **инлайновый `transform`** — и инлайн сильнее любой нашей таблицы стилей. То есть на
КАЖДОМ сегменте с движением масштаб слоя стирался, и черновик снова показывал двукратный кроп.
Найдено это не линейкой (она неподвижна), а первой живой сборкой `VID-02a`.

`FACT` (дифференциальная проба, `still@1` + `kenburns@1`, MAD по яркости между кадром
`draftHalf` и уменьшенным кадром `final`):

| правка | MAD с `kenburns@1` | MAD без него (контроль) |
|---|---|---|
| `transform: scale()` на `.layer` | **34.4134** | 0.1947 |
| **`zoom` на `.layer`** | **0.3184** | 0.1947 |

`zoom` от этого свободен по построению: GSAP его не пишет и не читает, свойства ортогональны,
и инлайновая трансформа шаблона применяется ВНУТРИ уменьшенной системы координат. Цена, которую
`zoom` берёт взамен, названа честно — он меняет РАСКЛАДКУ; измерение выше и есть проверка того,
что реализациям это безразлично: доли считаются от той же геометрии, в которой потом рисуются.

**ОХРАННИК ИСПРАВЛЕН ТАМ ЖЕ.** `scale-render.test.ts` получил ДВИЖУЩУЮСЯ пробу (`still@1` +
`kenburns@1`) с порогом MAD 2 при измеренных 0.3184. Показан падающим (Н4): 32.7262 против
порога 2.

**Почему `zoom` не годится на `#root`** (измерено раньше): он упирается в ту же вендорскую
перезапись и даёт те же 270×480 из 540×960.

**Побайтовая устойчивость трансформы между прогонами** доказана не рассуждением, а гейтом:
шесть шаблонов × N = 3 прогона — «различных framemd5: 1; различных sha256: 1» у каждого (§4).

**Отпечаток не тронут.** `launch.args` — закрытый список `FIXED_RENDER_ARGS`, CSS композиции в
`engineFingerprint` не входит (`fingerprint.ts`: версии внешних зависимостей + фиксированные
токены). Отпечаток после правки — `3217a4cf…`, тот же.

## 7. Что владельцу придётся сделать РУКАМИ при первой сборке — одна команда

**Первая сборка проекта с ПРОГРЕТЫМ кэшем `draftHalf` ОТКАЖЕТ**, и это не поломка, а
спроектированное поведение `CACHE-01`. Наблюдалось дословно на `examples/pompeii-30` и
`work/asset-test`:

```
сегмент 1/3 `seg:eruption`: 284 кадров, bundle 1a97654fab33…
  кэш: промах по композиции (запись снята на bundle 2c17e3df7ca4…)
vpe: K3: стадия `segment`, ключ `6a31aa69…`: под ним уже лежит значение с sha256 `56bf44d1…`,
     а кладётся `b780ecd4…`
```

Причина названа в самом сообщении и в долге №200: **`bundle.hash` в `segmentKey` не входит**
(ключ — функция IR, профиля и отпечатка), а композиция чернового профиля изменилась. K3 ловит
это ОТКАЗОМ, а не тихим пересчётом, — то есть охранник сработал ровно так, как задуман.

Лечение — одна команда на проект:

```bash
rm -rf <проект>/.cache/segment/draftHalf
```

Выполнено в этой сессии для `examples/pompeii-30`, `work/asset-test`, `examples/vertical-v1`
(у `examples/ai-test-1` каталога `draftHalf` не было). После очистки обе сборки прошли:
