## Пять находок входа, которые меняют постановку задачи

Записаны до плана, потому что три из них меняют ответ на обязательный вопрос и на состав кода.

**1. Схема записи ledger'а УЖЕ СУЩЕСТВУЕТ и она `.strict()`.** `S-02` завёл семейство `anchors/1`
(`packages/schema/src/families/anchors.ts`, `AnchorEntrySchema`) с полями ADR-0004 §4 дословно:
`id, chapterId, sceneId, ordinal, surface, prev, next, status, mintedAtRev, origin`. **Поля `boundTo`
в ней нет**, а `.strict()` означает, что добавить его нельзя, не правя схему. Это совпадает с ADR:
`boundTo` перечислен в §7 среди полей **записи overrides** («`reason`/`createdAt`/`boundTo`»), а не
записи ledger'а. Отсюда решение (вопрос 3): `boundTo` здесь — **функция над текущим разбором**, а не
поле ledger'а. Заодно `renderFamily('anchors', records)` из `S-02` уже умеет писать канонический
JSONL с шапкой первой строкой — писателя с нуля здесь не будет.

**2. Фикстура называет ожидаемые имена битов, и они отвечают на половину обязательного вопроса.**
`fixtures/minimal/direction/01-intro.yaml`, комментарий в шапке: «их порождает компилятор, привязывая
к неявным битам `b:img-harbour-1`, `b:img-ledger-1`, `b:img-sea-1`». В сцене `turn` **два** `[img:]`
(`ledger` и `sea`), поэтому счёт «все `[img:]` в области» дал бы `b:img-sea-2` (по сцене) или
`b:img-sea-3` (по файлу), а не `-1`. **Утверждение отчёта `C-02` §6.1 «в фикстуре все три `[img:]` …
по одному на сцену, поэтому все четыре комбинации дают одно и то же имя» неверно**: фикстура
различает «что считается» (и говорит: по alias), но не различает область (каждый alias встречается
один раз). Это не аргумент за решение — комментарий в фикстуре решением владельца не является, —
но это уже закоммиченный артефакт, и расхождение с ним нужно принимать осознанно.

**3. Обе «сценные» комбинации ordinal ломают A3.** `b:img-<alias>-<n>` со счётом внутри сцены даёт
**одинаковую строку** для одного alias в двух сценах одного файла (`b:img-sea-1` и `b:img-sea-1`).
A3 требует уникальности живых id, а лексер `C-02` уже проверяет уникальность имён `b:` внутри файла
(отчёт `C-02` §6.4). То есть буква ADR («`ordinalВСцене`») и инвариант A3 противоречат друг другу
на реальном сценарии «одно фото в двух сценах». Разбор — в вопросе 1.

**4. `publicAnchor()` отвергает `w:` — а ledger состоит в основном из `w:`.** В задании конструктор
бренда `AnchorId` валидирует «регуляркой `publicAnchor`»; `publicAnchor()` (`families/common.ts`)
именно затем и написан, чтобы **отвергать** `w:` (это исполнимая форма A1). Валидируя им, мы не
смогли бы построить ни одного id токена. Разбор и предложение — вопрос 2.

**5. `core-model` не умеет читать диск (M3), значит «чтение `anchors.lock.jsonl`» здесь — разбор
ТЕКСТА.** Как у лексера `C-02`: вход — строка, файл читает вызывающий. `renderFamily` — чистая
функция и зовётся из `core-model` без оговорок; а вот `readFamily` принимает **путь** и импортирует
`node:fs`, поэтому переиспользован быть не может. Разбор — вопрос 4.

## План (6 шагов)

### Шаг 1. Бренд `AnchorId` + минт `w:` — `packages/schema/src/types/brands.ts`, `packages/core-model/src/anchors/mint.ts`

Бренд — единственная разрешённая правка `@vpe/schema` (долг `C-01`, зафиксирован в
`packages/core-model/README.md`). **Регулярка не копируется**: конструктор валидирует через уже
существующую схему семейства — `AnchorEntrySchema.shape.id.safeParse(value)`, — поэтому алфавит id
остаётся объявленным ровно один раз (то же рассуждение, что в `C-02` §3.4 про `publicAnchor`).

```ts
export type AnchorId = Brand<string, 'AnchorId'>;              // любое пространство, включая w:
export type PublicAnchorId = AnchorId & Brand<string, 'PublicAnchorId'>;   // b:/sc:/ch:/r: — см. вопрос 2
export function asAnchorId(value: string): AnchorId;           // через AnchorEntrySchema.shape.id
export function asPublicAnchorId(value: string): PublicAnchorId; // через publicAnchor()
```

Минт — отдельный файл, ровно чтобы недетерминизм жил в одном месте:

```ts
export type RandomBytes = (n: number) => Uint8Array;   // порт: тесты подставляют свой, моков vi.mock не нужно
export const csprng: RandomBytes;                      // единственный импорт `node:crypto` в core-model
export function mintAnchorId(random: RandomBytes = csprng): AnchorId;  // `w:${base32(random(16))}` [:16]
```

16 байт = 128 бит (ADR-0004 §4); `base32(16 байт)` даёт 26 символов, берутся первые 16. Длина и
алфавит проверяются регуляркой семейства, а не глазами. Про линт на `node:crypto` — вопрос 8.

### Шаг 2. Ledger: чтение, запись, add-only, уникальность — `src/anchors/ledger.ts`

```ts
export interface Ledger { readonly records: readonly AnchorEntry[]; readonly rev: number; }
export function parseLedger(text: string, file: string): Ledger;   // текст, НЕ путь (M3)
export function renderLedger(ledger: Ledger): string;              // через renderFamily('anchors', …)
export function assertAddOnly(previousText: string, next: Ledger): void;   // диф старого префикса — ошибка
export function liveAnchors(ledger: Ledger): Map<AnchorId, AnchorEntry>;   // свёртка: последняя запись id
export function assertUniqueLive(ledger: Ledger): void;                    // A3
```

Четыре решения, которые здесь принимаются явно (все — прямые следствия ADR, не изобретения; если
владелец читает иначе — это вопросы, а не решения):

* **Канонический порядок = порядок дописывания.** ADR-0005 §10 задаёт «строка = запись, add-only»
  и не задаёт сортировки. Любая сортировка (по id, по сцене) переставляла бы строки при каждом
  минте и уничтожала бы add-only: merge перестал бы быть объединением множеств. Поэтому «канон» у
  этого файла = шапка + записи в порядке появления, и проверяется он **префиксом**, а не сортировкой.
* **Add-only исполним как «старый текст — префикс нового»** (после шапки, построчно). Изменение или
  удаление любой существующей строки — ошибка с номером строки и обеими её версиями.
* **Смена статуса — новая запись:** копия записи с `status: 'dead'`; `mintedAtRev` **не меняется**
  (поле называет ревизию минта, а не смерти), иначе запись «менялась бы».
* **«Живой» — по свёртке.** Живым считается id, у которого ПОСЛЕДНЯЯ запись имеет `status: 'live'`.
  Наивный греп по живым строкам считал бы живым каждый помеченный мёртвым якорь. Коллизия (A3) =
  два живых id, совпавших строкой, но различающихся телом записи (сцена/ordinal/surface) — ровно
  последствие merge двух веток, ради которого §4 и отверг детерминированный минт.

`mintedAtRev`: ADR его не определяет (`INFERENCE`). Берётся `rev = max(mintedAtRev) + 1` для записи,
которая что-то дописывает; у пустого ledger'а первая ревизия — `1`. Величина выводима из самого
файла, то есть merge её не ломает и внешнего счётчика не требует.

### Шаг 3. `boundTo` — `src/anchors/boundto.ts`

```ts
export function boundTo(context: { prev: string | null; surface: string; next: string | null; ordinal: number }): Blake3;
export function boundToOfCurrent(document: SourceDocument, id: AnchorId): Blake3;   // контекст из СВЕЖЕГО разбора
export function assertBoundTo(id: AnchorId, expected: Blake3, actual: Blake3): void; // §6: не сошлось ⇒ ошибка
```

Вход собирается `canonicalJson([prev, surface, next, ordinal])` — массивом, а не конкатенацией:
`("ab","c")` и `("a","bc")` обязаны давать разные хэши (тест). ADR-0004 §6 пишет функцию через
запятую и конкатенации не требует.

### Шаг 4. Word-diff и синхронизация ledger'а — `src/anchors/diff.ts`, `src/anchors/sync.ts`

```ts
export function diffTokens(before: readonly string[], after: readonly string[]): TokenMatch[];
export function syncLedger(document: SourceDocument, previous: Ledger, options: { random?: RandomBytes }): SyncResult;
// SyncResult: { ledger, minted: AnchorEntry[], died: AnchorEntry[], text: string }
```

**Алгоритм — LCS по поверхностным формам, посценно, с отрезанием общего префикса и суффикса.**
Обоснование и цена, раз ADR алгоритм не задаёт и библиотеку брать нельзя: LCS — 25 строк и точный
максимум совпадений; Myers быстрее по константе, но это тот же результат за большее число строк.
Стоимость `O(n·m)` времени и памяти (`Int32Array`) на сцену: в фикстуре сцены по ~60 токенов
(≈3600 ячеек, микросекунды), на сцену в 3000 токенов — 9·10⁶ ячеек (~36 МБ). Поэтому: (а) счёт
посценно, а не по файлу; (б) отрезание общих концов; (в) **жёсткий предел** `n·m > 4·10⁶` —
громкая ошибка «сцена слишком велика для диффа», а не тихая деградация. Замер на фикстуре пойдёт
в отчёт.

Что делает `syncLedger`: совпавшие токены наследуют id; новые — минтят; исчезнувшие получают запись
`dead`. Именованные якоря (`sc:` из `## scene:`, `b:` из `[beat:]`) минта не требуют — их id даёт
автор, — но в ledger записываются с `origin: 'token'` (ADR-0004 §2a говорит про неявные биты
«наравне с авторскими битами», то есть авторские там есть). Про `ch:` — вопрос 6.

**Контекст токена (`prev`/`next`) в записи — контекст МОМЕНТА МИНТА и потом не переписывается.**
Это следствие того, что запись не меняется (§4 add-only): правка соседнего слова не порождает
никакой новой записи для уцелевшего якоря, она меняет только его **текущий** контекст, а сверка
`boundTo` идёт против свежего разбора (§6). Иначе пришлось бы или менять запись (нельзя), или
дописывать вторую живую запись с тем же id (неотличимо от коллизии merge).

## Вопросы (ответ «ок» = принять все рекомендации; вопрос 1 требует выбора)

**1. Ordinal `<n>` в `b:img-<alias>-<n>` — обязательный.** Все четыре комбинации, имена на фикстуре
(`harbour` в сцене `intro`; `ledger` и `sea` — оба в сцене `turn`) и цена:

| # | что считается | область | имена на фикстуре | какие правки меняют ЧУЖИЕ id | коллизия одного alias в двух сценах |
|---|---|---|---|---|---|
| **а** | все `[img:]` | сцена | `harbour-1`, `ledger-1`, **`sea-2`** | вставка/удаление любого `[img:]` выше в **той же сцене** переименовывает все последующие биты сцены, включая чужие alias'ы | **да** — оба первые в своих сценах ⇒ одинаковая строка |
| **б** | все `[img:]` | файл | `harbour-1`, **`ledger-2`**, **`sea-3`** | вставка `[img:]` в первую сцену переименовывает биты **во всём файле** — худшая локальность, прямо против принципа ADR-0010 §3a («счётчик локален для сцены») | нет |
| **в** | только с этим alias | сцена | `harbour-1`, `ledger-1`, `sea-1` | только свой alias и только в своей сцене | **да** — `b:img-sea-1` в двух сценах |
| **г** | только с этим alias | файл | `harbour-1`, `ledger-1`, `sea-1` | только свой alias: вставка `[img: sea]` выше по файлу сдвигает последующие `sea` и никого больше | нет |

**Рекомендую «г».** Три довода: (1) единственная комбинация, которая и совпадает с уже закоммиченными
именами в `fixtures/minimal/direction/01-intro.yaml`, и **не может** породить дубль живого id —
а дубль живого id это A3, то есть громкая остановка сборки на совершенно законном «одно фото в двух
сценах»; (2) минимальный churn: правка одной картинки не переименовывает чужие; (3) «в» отличается
от «г» только в сценарии, где alias повторяется — и в этом сценарии «в» ломается.
**Цена «г», принимаемая явно:** буква ADR-0002 §4 и ADR-0004 §2a говорит `ordinalВСцене` ⇒ обе
строки требуют правки (замена «в сцене» на «в файле, среди `[img:]` с этим alias»). Правку ADR делает
владелец; до неё расхождение идёт в `DEBTS.md` строкой с адресом. Если правка ADR нежелательна —
второй выбор «в» **плюс** явный отказ `AnchorLedgerError` на повторе alias между сценами (обход для
автора: второй alias на тот же sha в `aliases.yaml`, файл это позволяет). Счёт `<n>` 1-based в любом
варианте (`paragraphOrdinalInScene` тоже 1-based).

**2. Бренд `AnchorId` против `publicAnchor()`.** В задании конструктор валидирует регуляркой
`publicAnchor`, но она **отвергает `w:`** (это её работа — исполнимая форма A1), а ledger почти
целиком из `w:`. Рекомендую **два конструктора и два бренда** в `brands.ts`: `AnchorId` (валидация
через `AnchorEntrySchema.shape.id` — пространства `w:`/`b:`/`sc:`/`ch:`/`r:`) и `PublicAnchorId`
(валидация через `publicAnchor()`), где `PublicAnchorId` — подтип `AnchorId`. Тогда A1 становится
**типовым**: значение с `w:` невыразимо там, где объявлен `PublicAnchorId`. Альтернатива, если это
лишнее: один бренд `AnchorId` с ledger-регуляркой, `publicAnchor()` остаётся только схемной проверкой.

**3. `boundTo` — функция, а не поле записи ledger'а.** В `AnchorEntrySchema` (уже закоммичена, `.strict()`)
такого поля нет; ADR-0004 §7 перечисляет `boundTo` среди полей **overrides**. Подтвердите, что
`C-04` даёт функцию `boundTo(...)` и сверку `assertBoundTo(...)`, а хранится значение в записи
override (`O-01`). Иначе нужна правка схемы вне `brands.ts` — а она заданием запрещена.

**4. Чтение JSONL внутри `core-model`.** `readFamily` принимает **путь** и импортирует `node:fs`,
поэтому в `core-model` (M3) не зовётся. Варианты: **(а)** свой разбор текста в `ledger.ts` — 15 строк
(разрезать по `\n`, пропустить шапку, `AnchorEntrySchema.safeParse` на строку); схема не дублируется,
дублируется только цикл; **(б)** вынести из `read.ts` чистую `parseFamilyText(text, filePath)` и
оставить `readFamily` обёрткой — тогда обе стороны читают одним кодом, но это правка `@vpe/schema`
**вне `brands.ts`**, то есть нужно ваше разрешение. Рекомендую **(б)** — ровно одна функция
переезжает, поведение не меняется; при «нет» беру (а) и записываю долг.

**5. `recordId` у порождённой `[img:]`-записи.** ADR-0002 §4 перечисляет дефолты (`track`, `z`,
`until`, `template`) и `recordId` **не называет**, а схема `direction/1` требует его у каждой записи
(`[0-9a-f]{8}`, «выдан CLI»). Компилятор выдать случайный не может: `recordId` — вход seed'а (ADR-0007 §1),
случайный на каждом прогоне убил бы D1/D10. Варианты: **(а)** golden показывает форму **без**
`recordId` (запись не проходит `DirectionSchema` как есть — расхождение записывается в `DEBTS.md`
с адресом `C-05`); **(б)** детерминированный `recordId = blake3('img-record' ‖ <id бита>)[:8]` — стабилен,
merge-безопасен (id бита уникален), но это правило, которого в ADR нет. Рекомендую **(а)**: «чего в
ADR нет — не добавлять», а `C-05` всё равно открывает эту тему как валидацию `direction/**`.
От ответа зависит статус D3 (в варианте «а» — пометка без смены статуса).

**6. `ch:` в ledger'е.** `AnchorEntrySchema.sceneId` — непустой идентификатор, а у якоря главы сцены
нет; вписать туда первую сцену значило бы соврать в машинном файле. Рекомендую **`ch:` в `C-04` в
ledger не писать** (в `sc:`/`b:`/`w:`/`b:img-…` он не нужен, а `until: ch:main` из фикстуры
резолвится по структуре AST, а не по ledger'у), и записать это долгом с адресом `O-01`/`L-03`.

**7. «Мёртвые хранятся N ревизий» (§4).** `N` не задано ни в одном документе, а удаление старых
записей прямо противоречит add-only (§4 и ADR-0005 §10). Рекомендую: **не удалять ничего**, долг в
`DEBTS.md` с условием открытия («ledger вырос настолько, что мешает диффу»).

**8. Линт на `node:crypto` вне файла минта — делать или нет.** Ровно тот же приём, что у `ms.ts`,
`brands.ts` и `canonical/json.ts`: `crypto` запрещён в `packages/core-model/src/**`, единственное
исключение — `src/anchors/mint.ts`, охранник — `tests/lints/` (греп + программный ESLint по
файлу-нарушителю). Плюс: «недетерминизм живёт ровно в одном файле» становится проверяемым.
Минус: ADR-0007 §4 такого запрета не содержит, это расширение правила D4 (как схлопывание пробельных
было расширением D8) — уйдёт пометкой у D4 и в `DEBTS.md`. Цена ~15 минут. Рекомендую **делать**.
