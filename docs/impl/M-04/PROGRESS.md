## Измерено ДО плана (12 минут, `ffmpeg 6.1.1`, зонд в scratchpad, в репозиторий не идёт)

Плановые решения ниже опираются не на память, а на семь измерений. Все воспроизводимы одной
командой; синтетика — `lavfi` (`testsrc`, `smptebars`), 320×240, 30 fps, PNG-последовательность.

1. `FACT` **PNG-последовательность кодируется**: `-framerate 30 -i f/%06d.png … -f mpegts`
   даёт `h264 High`, 90 пакетов на 90 PNG — ровно.
2. `FACT` **`nb_frames` у MPEG-TS отсутствует**; `ffprobe -count_packets` даёт
   `nb_read_packets = 90` **без декодирования**, `-count_frames` даёт то же 90 **с**
   декодированием. Значит измеренный `frameCount` сегмента стоит копейки, а не 1.345 с.
3. `FACT` **риск SP-3d §4.3 воспроизведён**. Последовательность с жёсткой склейкой на кадре 46:
   без `-sc_threshold 0` ключевые кадры встают на 1, 31, **46**, 76 — сетка GOP сбита сценой;
   с `-sc_threshold 0` + `-x264-params scenecut=0:open-gop=0` — ровно 1, 31, 61, то есть
   `gopSize = 30`. **На «спокойном» источнике риск НЕ виден** (без флага тоже 1, 31, 61) —
   значит негативный тест обязан иметь склейку внутри, иначе он ничего не стережёт.
4. `FACT` **`time_base` финала == `time_base` сегмента**: `.mts` → `1/90000`, и `-c copy`
   переносит эту же шкалу в `mp4` (`90k tbn`). То есть **R9 держится буквально**, вместе с
   `timeBase` из состава ADR-0008 — расхождения «TS против MP4» на этой версии ffmpeg нет.
   (Это было главное подозрение к R9 до измерения. Оно снято.)
5. `FACT` **шов точен**: 90 + 60 сегментов → `nb_frames = 150` у финала, `duration = 5.000000`;
   аудио 120000 сэмплов при 24000 Гц ⇒ `ceil(120000/800) = 150`. Тройное равенство **R8**
   сошлось на настоящем шве двух настоящих сегментов с точностью до кадра.
6. `FACT` **подпись энкодера доживает до финала в неизменном виде**. `-fflags +bitexact
   -flags:v +bitexact` SEI x264 **НЕ вырезает** (проверено `strings`): строка
   `x264 - core 164 … options: … keyint=30 … scenecut=0 … crf=18.0 … threads=4` лежит и в
   `.mts`, и в `final.mp4`. Сравнивать её **в контейнере нельзя** (в TS её режут 188-байтные
   заголовки пакетов), а в элементарном потоке — можно: `ffmpeg -c copy -f h264` из сегмента и
   из финала (`-bsf:v h264_mp4toannexb`) дают **побайтово равный** блок SEI. Это и есть
   «`encoderSettings` из `ffprobe`», обещанный охранник **R10**, в исполнимой форме.
   Оговорка, тоже измеренная: элементарные потоки ЦЕЛИКОМ (a+b против финала) **не равны** —
   32288 против 32143 Б, расходятся с байта 4527 (SPS/PPS/AUD на шве). Значит охранник — SEI,
   а не «склей и сравни».
7. `FACT` **детерминизм энкода**: два прогона одного PNG-сиквенса одной версией ffmpeg при
   `threads=4` дают **побайтово равный** `.mts` и равный `framemd5`. Оговорка: `framemd5`
   с `-c copy` считает хэши ПАКЕТОВ, а не декодированных кадров — то есть под флагом
   `--verify-frames` обязан идти без `-c copy` (ADR-0006 §14: «md5 каждого декодированного
   кадра», 1.345 с/сегмент — цена именно за декод).

`FACT`, найденный попутно и неприятный: x264 **молча зажимает** `rc_lookahead` до `keyint`.
Профиль просит `rcLookahead: 40` при `gopSize: 30`, SEI финала показывает `rc_lookahead=30`.
То есть «полная строка энкодера из профиля» исполняется не дословно. Это кандидат в долг
(вопрос 4b ниже), а не повод молча округлить.

## План (жду «ок»)

**[1/6] `assemble/ffprobe.ts` — измерение, и только оно.** Второй подпроцессный файл пакета
(первый — `audio/ffmpeg.ts`, `M-03`), `ffprobePath` входом, `DEFAULT_FFPROBE_PATH = 'ffprobe'`,
`readFfprobeBuild` по образцу `readFfmpegBuild` (отсутствие бинарника — падение с лечащим
сообщением, тихого skip нет). Разбор JSON `ffprobe -show_streams` — **чистая функция**
`parseStreams(json)`, покрываемая без подпроцесса. Поверх неё:
`probeStreamFingerprint(path)` → `StreamFingerprint` (состав — вопрос 3),
`probeFrameCount(path)` → число (`-count_packets`, измерение 2),
`probeHasAudio(path)` → `boolean` (**R5**), `probeKeyframeIndices(path)` → `readonly number[]`.
Ни одно значение не приходит из профиля: всё, что возвращает этот файл, измерено.

**[2/6] `assemble/encode.ts` — кодирование сегмента.** Чистая `segmentEncodeArgs(options)` →
`string[]` (голден-вектор на массив целиком, как `resampleArgs` в `M-03`) и тонкая
`encodeSegment(options)` поверх `runFfmpeg`. Вход кадров — **PNG/JPEG-последовательность**
(вопрос 1). Из `render-profile/1` дословно: `codec`, `crf`, `gopSize` (`-g` + `-keyint_min`),
`pixelFormat`, `colorSpace`, `encoder.{threads,preset,tune,rcLookahead,aqMode,psy,bitexact}`;
явно и всегда — `-sc_threshold 0` + `-x264-params scenecut=0:open-gop=0` (измерение 3) и
**`-an`** (**R5**). `fps` — из `compile-profile/1` (в `render-profile/1` его нет и не должно
быть). Контейнер выхода — `mpegts`, расширение `.mts`. `tune: none` в командную строку **не
уезжает**: `-tune none` ffmpeg не понимает — «none» здесь означает «тюна нет» (проверю и
запишу фактом).

**[3/6] `assemble/concat.ts` — конкат и единственный энкод аудио.** Чистая
`concatMuxArgs(options)` → `string[]` (вопрос 2: **демуксер `-f concat -safe 0`**) и
`concatAndMux(options)`. Одна команда ffmpeg делает ровно две вещи: `-c:v copy` (**R10**) и
`-c:a aac -b:a 192k -ar 48000` из `audio-profile/1` (**единственный энкод аудио**, вопрос 4).
Список конката пишется через `writeAtomic` (`M-01`, K7), пути абсолютные, кавычки экранируются.
Рядом — **денай-лист**: `assertNoVideoEncodeArgs(args)`, чистая функция, которой и стережётся
R10 в форме «тест командной строки ffmpeg».

**[4/6] `assemble/verify.ts` — проверки после конката.** `verifyAssembly(...)`:
**R8** — тройное равенство `Σ durationInFrames == frameCount(final) ==
ceil(N_samples / samplesPerFrame)`, где `samplesPerFrame` и `ceilDiv` берутся из
`@vpe/core-model` (своей арифметики нет), `frameCount` — измеренный, `N_samples` — из PCM;
расхождение в 1 кадр — `AssembleError`, а не WARN. **R9** — `assertSameFingerprint(final,
firstSegment)` с ПОИМЁННЫМ перечислением разошедшихся полей в сообщении. **R5** — отказ, если
`probeHasAudio(segment)`. **Закрытость GOP** — `assertClosedGop(keyframes, gopSize)`: позиции
I-кадров обязаны быть ровно `0, gopSize, 2·gopSize, …`. Плюс `assertSameEncoderSei(final,
firstSegment)` — измерение 6, вторая половина R10.

**[5/6] `assemble/framemd5.ts` — под флагом, вне обычного пути.** `framemd5Of(path)` с
декодированием (без `-c copy`, измерение 7) и `FRAMEMD5_FLAG = '--verify-frames'`.
Охранник того, что она **не** зовётся в обычной сборке: `assembleSegments`/`concatAndMux` её
не импортируют, и это проверяется тестом-грепом по исходникам, а не обещанием (ADR-0006 §14).

**[6/6] Тесты и доки.** `packages/media/test/assemble-*.test.ts`: синтетика через `lavfi`
(кадры генерируются кодом-вызовом, ни одного бинарника в репозитории — правило `M-03`);
позитив — два-три сегмента → конкат → все проверки зелёные; негативы — сегмент С аудио (R5),
сегменты с разным fingerprint (R9), усечённый сегмент (R8, расхождение ровно в 1 кадр),
последовательность со склейкой без `-sc_threshold 0` (закрытость GOP), денай-лист R10;
детерминизм — два прогона, сравнение `.mts` побайтово и по framemd5. Затем
`docs/impl/M-04/{report.md, PROGRESS.md, violation-transcript.txt}`, ревизия шапки
`docs/invariants.md` и переходы **по фактическому покрытию** (вопрос 5), обновление долга
SP-3 №5 в `roadmap` §7.3, новые долги — в `DEBTS.md`.

## Вопросы (решает владелец; до «ок» кода не пишу)

**1. Вход кадров в энкодер: PNG/JPEG-последовательность против rawvideo по pipe.**
`rawvideo` быстрее (нет PNG-энкода у писателя и PNG-декода у ffmpeg) и не трогает диск, но
на 1080×1920 это 6.2 МБ на кадр в трубе, и главное — он **противоречит форме, которая уже
записана**: `pixelProfile.imageFormat: jpeg|png` и `jpegQuality` существуют в `render-profile/1`
именно потому, что рендерер отдаёт КАДРЫ КАРТИНКАМИ; при rawvideo эти два поля не исполняет
никто. Цена последовательности: N файлов на диске в `tmpDir` и один лишний декод на кадр
(у `testsrc` 90 кадров 320×240 — 0.2 с; на 1800 кадрах 1080×1920 это `UNKNOWN`, мерить в `F-01`).
**Рекомендую последовательность**, формат — из `pixelProfile.imageFormat`.
*Оговорка, входящая в вопрос (`INFERENCE`):* ADR-0008 описывает `SegmentArtifact` как то, что
отдаёт **рендерер** (там `path`, `framemd5Sha256`, `stream`), а roadmap `M-04` требует, чтобы
сегменты кодировал **наш** ffmpeg. Из двух это следует читать так: рендерер отдаёт кадры,
`media` их кодирует, `SegmentArtifact` собирает `media`. Это **кандидат в правку ADR-0008**,
и я его не правлю — записываю в отчёт.

**2. Конкат: демуксер против `concat:`-протокола.** `concat:` для MPEG-TS дешевле (склейка на
уровне байт), но каждый файл несёт СВОЙ отсчёт PTS — измерено: `start_pts = 132000`
(1.466667 с) у обоих сегментов, то есть при байтовой склейке шкала времени на шве **сбрасывается
назад**, и `frameCount`/`duration` финала перестают быть тем, что мы проверяем в R8. Демуксер
открывает каждый файл отдельно и сам сдвигает таймстемпы на накопленную длительность — на
измерении 5 это дало ровно 150 кадров и 5.000000 с. Цена демуксера: файл-список на диске и
экранирование путей. **Рекомендую демуксер** `-f concat -safe 0`.

**3. Состав `StreamFingerprint`.** ADR-0008 уже называет десять полей:
`codec, profile, level, pixFmt, colorSpace, timeBase, width, height, fpsNum, fpsDen`.
**Предлагаю взять их все и ничего не добавлять** — измерение 4 сняло единственное возражение
(`timeBase` совпал: `1/90000` и там, и там). Что НЕ входит и почему: `bit_rate`, `nb_frames`,
`duration`, `start_pts` (различны у сегмента и финала по построению — это не отпечаток потока,
а его размер), `color_range`, `chroma_location`, `has_b_frames`, `refs`, `extradata_size`
(каждое лишнее поле — ложное падение между сборками ffmpeg, а не пойманная ошибка).
`fpsNum/fpsDen` беру из `r_frame_rate` (базовая частота), не из `avg_frame_rate` (у усечённого
файла он «плывёт» и превратил бы R9 в дубль R8). Нужен ли `colorRange` одиннадцатым — скажите.

**4a. Контейнер финала и аудио-кодек мукса — поля НАЙДЕНЫ, схему трогать не нужно.**
Контейнер: `final.mp4` — ADR-0005 §67 (раскладка `build/`: «`segments/*.mts`, `audio/track.wav`,
`final.mp4`») и `core.md` §590. Аудио: `audio-profile/1` — `codec: aac`, `bitrateKbps: 192`,
`deliverySampleRate: 48000` (`fixtures/minimal/profiles/audio.yaml`). Беру дословно.
**4b. Из этого следует то, чего никто не решал, и я обязан спросить:** тракт живёт на
`projectSampleRate = 24000`, а доставка — 48000, то есть **при муксе происходит ресемплинг**
речи 24000 → 48000. `M-03` записал правило «ресемплинг ровно один раз, на ingest» — оно про
музыку, и формально не нарушено, но второй ресемплинг в тракте появляется здесь. Сам профиль
это знает и помечает `UNKNOWN` («почему 48000, а не 24000 — тогда ресемплинга нет»), адрес —
`X-02`. Вопрос: **писать ли параметры ресемплера явно и на этом шаге** (`-af
aresample=resampler=soxr:precision=28`, как в `M-03`) или оставить умолчание `aac`-энкодера?
Рекомендую **явно** — по той же причине, по которой это сделано в `M-03`: умолчание версии
ffmpeg исполняет профиль не дословно. Плюс завожу долг «второй ресемплинг в тракте, адрес
`X-02`». **4c.** `-movflags +faststart` в мукс — ставить? Он делает второй проход по файлу
(перенос `moov` в начало) и нужен для веб-раздачи; ADR о нём молчит. Рекомендую **не ставить**
в `M-04` и вернуться к нему в `G-*` (публикация): «второй проход по файлу» в задаче про
единственность энкода лучше не заводить молча.

**5. Полное покрытие R5/R8/R9/R10 без настоящего рендерера — построчно, честно.**
* **R5** («в сегменте нет аудио-дорожки») → **`guarded` без оговорок.** Сегменты в v1 кодирует
  `media`, а не рендерер (риск SP-3d §4.3), то есть правило целиком исполняется здесь: `-an` в
  аргументах + измеренный `probeHasAudio` + негативный тест с сегментом, у которого дорожка есть.
* **R8** (тройное равенство) → **`guarded`.** Все три величины вычислимы здесь: `frameCount`
  измерен ffprobe, `N_samples` — из PCM `M-03`, `Σ durationInFrames` — вход. Оговорка, которую
  впишу в строку инварианта: третье слагаемое сегодня приходит из ТЕСТА, а не из компилятора
  (`CP-01` не написан), поэтому охраняется **ассерт**, а не «компилятор посчитал верно».
* **R9** (отпечаток финала == первого сегмента) → **`guarded`**, при ответе «все десять полей»
  на вопрос 3. Измерение 4 показало, что буквальная формулировка ADR исполнима.
* **R10** («видео кодируется ровно один раз; конкат только `-c copy`») → **`guarded`**, обе
  половины охранника из строки инварианта существуют: денай-лист по аргументам (шаг 3) и
  подпись энкодера из потока (измерение 6). Оговорка: «ровно один раз» проверено на пути
  `кадры → наш энкод → конкат`. Путь «рендерер отдал уже закодированный сегмент» здесь не
  существует и появиться не может — но если ADR-0008 останется в нынешней редакции (вопрос 1),
  он вернётся, и тогда R10 придётся перепроверять в `H-*`. Это пишу в строку инварианта.
* **Долг SP-3 №5** («шов `concat -c copy` двух настоящих сегментов») → **сужается, не
  закрывается.** Здесь впервые проверяется ШОВ (измерение 5: 90 + 60 = 150 кадров ровно), но
  сегменты **синтетические**, а долг говорит «двух НАСТОЯЩИХ». Настоящие — это выход
  HyperFrames на многосегментной фикстуре, то есть `F-01`. Предлагаю переписать строку §7.3
  как «шов проверен на синтетике в `M-04` (точность до кадра, отпечаток совпал); остаётся
  `F-01` — шов кадров рендерера».
