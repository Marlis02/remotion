> Маркировка утверждений: **FACT** (со ссылкой) / **PRACTICE** (индустриальная практика) / **INFERENCE** (мой вывод из фактов) / **UNKNOWN** (не проверено — нужен спайк).

## 0. TL;DR

**RECOMMENDED RENDERING ARCHITECTURE: гибрид из трёх слоёв, где Remotion — только слой кадров.**

```
[Project Model + overrides]  →  [RenderIR]  →  [Frame Renderer]  →  [Assembly]
      zod / SQLite            renderer-        Remotion            ffmpeg
                              agnostic         (Chromium)          (concat + mux + encode)
```

1. **Frame Renderer = Remotion** — рендер глав (chapters) в немые видео-сегменты.
2. **Assembly = ffmpeg напрямую** — конкатенация сегментов + подмешивание одной сплошной аудио-дорожки + единственное финальное кодирование.
3. **Между моделью проекта и Remotion — свой `RenderIR`**, не зависящий от Remotion. Это единственное решение, которое реально страхует от переписывания.

**Почему Remotion, а не остальные:** это единственный кандидат, который одновременно даёт (а) типографику уровня браузера — критично для субтитров-по-словам из V1, (б) живой проект (релиз v4.0.513 от 2026-08-18), (в) **first-party механику сегментного рендера и склейки** (`frameRange`, `compositionStart`, `h264-ts`, `separateAudioTo`, `combineChunks()`), которая ровно совпадает с инвариантом V4.

**Главные trade-off'ы, которые мы принимаем:** Remotion — самый медленный и самый прожорливый по памяти из четырёх кандидатов, и у него **платная лицензия для «автоматизаций»**, статус которой для соло-разработчика нужно уточнить письменно (см. §9.1 — это риск №1, и он юридический, а не технический).

**Что заложить сейчас (детали в §8):** `RenderIR` + глава как единица рендера и кэша + видео-сегменты без звука + аудио одной PCM-дорожкой + `renderProfile` (версии/шрифты/кодеки) внутри ключа кэша.

## 2. Кандидат A — Remotion

React + Chromium: каждый кадр — это скриншот веб-страницы, кадры кодируются ffmpeg'ом.

### 2.1 Что установлено фактами

* **FACT.** Единица concurrency — вкладка браузера: *«concurrency refers to how many browser tabs are opened in parallel during a render»*, и *«Each Chrome tab renders web content and then screenshots it»*. Дефолт — половина CPU-потоков. [1][2]
* **FACT.** Есть `frameRange` — *«Specify a single frame … or a range of frames … to be rendered»*; в CLI `--frames=0-99,150-199`. [2][3]
* **FACT.** Есть `gopSize` — *«Set the maximum number of frames between two keyframes. This maps to FFmpeg's -g option. Default: Let the encoder decide.»* [2]
* **FACT.** Есть `separateAudioTo` — аудио выводится отдельным файлом, не в основной выход. Есть `muted`. Есть аудио-кодек `pcm-16`. [2][8]
* **FACT.** Кодек `h264-ts` (контейнер `.ts`) поддерживается штатно. [8]
* **FACT.** `random()` даёт детерминированный псевдослучай по seed; `Math.random()` явно не рекомендован, потому что *«Remotion renders a video on multiple threads and opens the website multiple times»*. Это ровно V8. [4]
* **FACT.** Версия Chrome прибита к версии Remotion: Remotion пишет файл `VERSION` (например `149.0.7790.0`), и *«If the VERSION file is missing … or does not match the expected version, Remotion will delete the existing browser and download the correct version»*. [11]
* **FACT.** Проект очень живой: 56 800 звёзд, последний push 2026-08-19, релиз v4.0.513 от 2026-08-18. [15]

### 2.2 Слабые места — тоже фактами

* **FACT.** *«⚠️ Memory leaks are a known problem with `angle`. We recommend to split up long renders into multiple parts when rendering large videos, since sometimes renders can fail due to memory leaks.»* [10] — то есть **сам Remotion советует то, что мы и так обязаны делать по V4**.
* **FACT.** *«On a machine with no GPU, `swangle` is recommended. Rendering might be slow.»* [10] И: *«By default in many cases, the GPU is disabled in headless mode, which can lead to a significant slowdown in rendering time.»* [9]
* **FACT (мина по памяти).** Два кэша по умолчанию берут **по половине системной памяти каждый**: `offthreadVideoCacheSizeInBytes` — *«The default is null, corresponding to half of the system memory available when the render starts»*; `mediaCacheSizeInBytes` — *«The default is half of the available system memory when the render starts»*. [2]
  **INFERENCE.** На ноутбуке 16 ГБ это два бюджета по ~8 ГБ поверх N вкладок Chrome. Оставлять дефолты нельзя — см. §6.1.

### 2.3 Вердикт по A

K1 — лучший в выборке. K5 — лучший в выборке (first-party, §6.3). K6 — лучший. K2/K3 — худший. K7 — риск лицензии (§9.1).

## 3. Кандидат B — Motion Canvas

TypeScript-генераторы + Canvas 2D, ориентирован на анимационные пояснительные ролики.

* **FACT (дисквалифицирующий).** Проект фактически спит. Последний релиз — **v3.17.2 от 2024-12-14**, то есть более 20 месяцев назад. По коммитам: один коммит 2026-07-02, до него — 2025-02-16. Репозиторий формально не архивирован (`"archived": false`), 18 971 звезда, 173 открытых issue. [16]
* **FACT.** Собственная документация про ffmpeg-экспортёр: *«The exporter is still relatively new and may not have all the features you need.»* [13]
* **INFERENCE.** Для проекта, у которого в acceptance criteria записан AC6 (миграция старых проектов на новые версии движка), ставка на спящий апстрим — это гарантия, что через год-два мы сами станем его мейнтейнерами. Для одного разработчика (§2) это неприемлемая нагрузка.
* **INFERENCE.** K1: Canvas 2D API не даёт ни автопереноса строк, ни flexbox-раскладки — типографику пришлось бы строить руками, то есть тот же объём работы, что и в кандидате C, но с чужим фреймворком сверху.

**Вердикт: отклонён по K7.** Это единственный кандидат, отклонённый по нетехнической причине, и я считаю её решающей.

*Замечание о добросовестности:* в обсуждениях встречается утверждение, что домен `motioncanvas.io` не резолвится и проект заброшен. Я проверил — **домен резолвится** (получил A/AAAA-записи), прямой HTTP-запрос вернул 403 (защита от ботов). Так что «сайт лежит» — неверно; верно более узкое: **релизов нет с декабря 2024**. Отклоняю по проверенному факту, не по слуху.

## 4. Кандидат C — свой Canvas/WebGL + ffmpeg pipe

Рисуем кадры сами (Skia/Canvas в Node), пишем сырые кадры в stdin ffmpeg.

* **FACT.** Живые кирпичи под это есть: `@napi-rs/canvas` (Skia, push 2026-08-19), `skia-canvas` (Skia), `node-canvas` (Cairo). Skia — тот же движок, что в Chrome. [17]
* **FACT.** Есть промежуточный вариант — `vercel/satori` (HTML/CSS → SVG, push 2026-07-24, 13 786 звёзд) + `resvg-js` для растеризации. [17]
* **INFERENCE.** K2/K3 — лучший вариант: нет Chromium, память предсказуема, кадр стоит ровно столько, сколько нарисовано. K4 — потенциально идеальный: полный контроль, никакого браузера.
* **INFERENCE (почему всё же не сейчас).** K1 и K6 обваливаются. Нужно самому реализовать: перенос строк, шейпинг, выравнивание, инлайновые стили в субтитрах, подсветку текущего слова, маски, блюры, тени — и **полностью своё превью**, потому что без превью цикл правки для одного человека умирает. Это не «модуль», это отдельный продукт. Satori снимает часть боли, но поддерживает лишь подмножество CSS, то есть библиотека эффектов всё равно будет ограничена его подмножеством.

**Вердикт: не сейчас, но это наш запасной аэродром.** Именно ради него в §8 вводится `RenderIR`: если K2 не влезет в AC2/AC3 на реальном железе, мы меняем backend, не трогая модель проекта.

* **FACT.** `drawtext` требует сборки с `--enable-libfreetype`, шейпинг — `libharfbuzz`, а `text_shaping` (в т.ч. RTL и арабская вязь) — `--enable-libfribidi`. Есть `line_spacing`, но **опции автоматического переноса строк нет**. [14]

## 7. Разбор победителя: Remotion в деталях

### 7.1 Реальные механизмы памяти

**Как устроено (FACT).** Remotion открывает N вкладок Chrome; каждая рендерит веб-контент и делает скриншот; N по умолчанию = половина CPU-потоков. [1][2] Поверх этого работают два независимых кэша, у каждого дефолт — **половина системной памяти**: `offthreadVideoCacheSizeInBytes` (кадры `<OffthreadVideo>`) и `mediaCacheSizeInBytes` (декодированное медиа для `<Video>`/`<Audio>` из `@remotion/media`). [2]

**INFERENCE — почему дефолты для нас опасны.** Дефолты рассчитаны на рендер-сервер, где машина занята только рендером. У нас (§2) — рабочий ноутбук, на котором параллельно живут IDE, браузер и Node. Два кэша по «половине памяти» + N вкладок Chrome + сам ffmpeg — это конфигурация, в которой OOM происходит не «если», а «когда», причём тем вероятнее, чем длиннее таймлайн.

**PRACTICE — что задать явно в `renderProfile`:**

| Параметр | Что поставить | Зачем |
|---|---|---|
| `concurrency` | явное число (начать с `cores/2`, подобрать `npx remotion benchmark`) | воспроизводимость: дефолт «половина потоков» плавает от машины к машине, а значит плавает и профиль памяти |
| `offthreadVideoCacheSizeInBytes` | явный лимит (напр. 1–2 ГБ) | иначе половина RAM [2] |
| `mediaCacheSizeInBytes` | явный лимит | иначе половина RAM [2] |
| `offthreadVideoThreads` | оставить 2 (дефолт) | *«Increase carefully, as too many threads may cause instability»* [2] |
| `disallowParallelEncoding` | `true` для длинных/тяжёлых глав | *«This makes the rendering process more memory-efficient, but possibly slower»* [2] |
| `--gl` | `swangle` на машине без GPU | рекомендация самого Remotion [10]; заодно уводит от протечек `angle` [10] |

**INFERENCE.** `--gl=swangle` — это осознанный размен: мы отказываемся от GPU-ускорения ради (а) отсутствия известных протечек `angle` и (б) одинакового софтверного растеризатора на любой машине, что прямо работает на AC4. Для нашего контента (текст, картинки, CSS-трансформы), а не Three.js, потеря скорости должна быть умеренной — но это **UNKNOWN до замера** (§10.1).

**FACT.** Ключевой архитектурный вывод даёт сам Remotion: при длинных рендерах *«We recommend to split up long renders into multiple parts»*. [10] То есть **память на long-form решается не настройками, а сегментацией** — а сегментация у нас уже есть как инвариант V4. Это редкий случай, когда ограничение инструмента и решение Charter'а совпали.

### 7.2 Практики для сотен сцен с изображениями

Это самый вероятный сценарий у нас: AC1 — 8 фото на 60 секунд, то есть long-form 20 минут — это порядка 150–200 изображений (**INFERENCE**, экстраполяция AC1).

* **PRACTICE.** Не монтировать все сцены сразу. В Remotion сцены заворачиваются в `<Sequence>`; вне своего интервала контент не смонтирован, и изображение не висит в памяти. Ошибка «отрендерить все 200 `<Img>` и спрятать через `opacity: 0`» удерживает все декодированные битмапы одновременно.
* **PRACTICE.** Предварительно ресайзить ассеты под целевое разрешение на этапе подготовки (ingest), а не подсовывать рендереру 4000×3000 из телефона. Декодированный битмап 4000×3000 — это ~48 МБ RSS против ~8 МБ у 1080×1920. Это прямо соответствует V9: рендерер «глупый», вся подготовка — заранее.
* **FACT + PRACTICE.** `staticFile()` сам применяет `encodeURIComponent`, и *«you must avoid to encode the filename yourself»* — иначе двойное кодирование. [6] Отсюда правило: имена файлов ассетов в хранилище делать ASCII-safe (например, по checksum из V10), тогда весь класс ошибок исчезает.
* **PRACTICE.** Изображения — через сборку/`staticFile()` из `public/`, а не по сети. Это V9 (в рендере нет сети) и одновременно защита от таймаутов `delayRender` (§7.5).
* **FACT.** Для видео-ассетов — `<Video>` из `@remotion/media`: *«`<Video>` from `@remotion/media` is the recommended component for embedding videos in Remotion»*, он извлекает кадры через Mediabunny. [12] Старые `<OffthreadVideo>`/`<Html5Video>` — легаси.

### 7.3 Рендер по сегментам + конкат: подводные камни

Здесь надо развести **две разные вещи**, которые легко перепутать — и цена путаницы высокая.

**(a) Chunking внутри одной композиции (механизм Remotion).** Одна композиция режется по `frameRange` на равные куски ради параллелизма. Remotion описывает это как first-party рецепт для своего распределённого рендера [7]:

* **FACT.** *«Every chunk must render the same amount of frames, except the last one. Violating this rule might lead to audio artifacts if you are using the aac audio codec.»*
* **FACT.** *«you must pass the same options for every chunk»*.
* **FACT.** `compositionStart` = первый кадр общего рендерируемого диапазона (при полной композиции — `0`).
* **FACT.** Для h264 чанки рендерить кодеком **`h264-ts`**, а не `h264`.
* **FACT.** `enforceAudioTrack: true`, `numberOfGifLoops: null` — всегда для чанка.
* **FACT.** Если чанк ≥ 4 кадров и аудио не AAC → `audioCodec: 'pcm-16'` и `forSeamlessAacConcatenation: false`. Иначе → `forSeamlessAacConcatenation: true`.
* **FACT.** Аудио чанка — отдельным файлом через `separateAudioTo`.
* **FACT.** Склейка — API `combineChunks()`, которому передаются `videoFiles`, `audioFiles`, `framesPerChunk`, `fps`, `compositionDurationInFrames`, `frameRange`, финальный `codec` (уже `h264`, не `h264-ts`).
* **FACT.** `forSeamlessAacConcatenation` — *«the audio is trimmed to the nearest AAC frame, which is required for seamless concatenation of AAC files … This option is used internally. There is currently no documentation yet for to concatenate the audio chunks.»* [2]

**(b) Сегментация по главам (наш инвариант V4).** Глава — отдельная композиция со своим содержимым и своим временем жизни в кэше. Это **не** то же самое, что chunking: у глав разная длина (правило «одинаковое число кадров» неприменимо), разные `inputProps` (правило «одинаковые опции» частично неприменимо), и главное — нам нужна **раздельная инвалидация кэша**, чего механизм (a) не даёт вообще.

**INFERENCE — как совместить.** Берём (b) как единицу кэша, но заимствуем из (a) все правила, которые не завязаны на равную длину чанков. И добавляем один ход, который убирает самый неприятный класс проблем:

> **Аудио не режется по сегментам вообще.** Главы рендерятся **немыми** (`muted: true`), звук собирается отдельной сплошной PCM-дорожкой на всю длину ролика и подмешивается один раз в конце.

**INFERENCE — почему это правильный ход.** Проблема стыков аудио существует потому, что AAC — фреймовый кодек с encoder delay: границы AAC-фреймов не совпадают с границами сегментов, отсюда щелчки и накопительный дрейф. `forSeamlessAacConcatenation` — это обходной приём именно для случая, когда резать аудио всё-таки надо. Нам не надо: **у нас уже есть V6** («сшивка аудио-чанков — в PCM/WAV, кодирование один раз в конце»). Применяя V6 не только к TTS-чанкам, но и ко всей аудио-дорожке ролика, мы делаем стыки аудио **несуществующей проблемой**, а не решённой. Заодно это выполняет AC5: субтитры синхронизируются с одной непрерывной дорожкой, а не с суммой сегментов, где ошибки складываются.

**Подводные камни видео-конката (FACT + INFERENCE):**

| Камень | Суть | Что делать |
|---|---|---|
| Несовпадение параметров | **FACT (ffmpeg):** *«All files must have the same streams (same codecs, same time base, etc.)»* [5] | Все параметры кодирования — из одного `renderProfile`, общего на все сегменты. Разрешение, fps, pix_fmt, timebase, `colorSpace` — не «по умолчанию», а явно |
| GOP / keyframe | При `-c copy` резать можно только по keyframe | Каждый сегмент рендерится независимо → начинается с IDR by design. Дополнительно задать `gopSize` явно (маппится в `-g` [2]), чтобы GOP не «решал энкодер» [2] |
| Таймстемпы и дырки | **FACT (ffmpeg):** *«The timestamps in the files are adjusted so that the first file starts at 0 and each next file starts where the previous one finishes. Note that it is done globally and may cause gaps if all streams do not have exactly the same length.»* [5] | Это ровно про **разную длину видео и аудио в сегменте**. Немые сегменты (одна дорожка) убирают причину целиком |
| Ошибка длительности | **FACT (ffmpeg):** *«if the duration is incorrect … it can cause artifacts»* [5] | Длина главы задаётся в кадрах в IR и проверяется `ffprobe` после рендера сегмента |
| Контейнер | MPEG-TS устойчив к конкатенации | Промежуточные сегменты — `h264-ts`/`.ts` [7][8], финальный ремукс в `.mp4` |
| Лишнее поколение кодирования | Пересжатие после конката = потеря качества | Сегменты кодируются **сразу с финальными параметрами**, конкат делается `-c copy`, второго энкода видео нет |

### 7.4 Границы детерминизма (что именно недетерминировано и почему)

Детерминизм у Remotion **не бесплатный и не полный**. Точные границы:

**Что детерминировано:**
* **FACT.** `random(seed)` — *«If the seed is the same, the output is always the same»*. [4] Это исполнение V8.
* **FACT.** Версия Chrome прибита к версии Remotion через файл `VERSION`, и при несовпадении браузер удаляется и перекачивается. [11] **INFERENCE:** значит, при фиксированной версии Remotion растеризатор один и тот же — база для AC4 есть.

**Что НЕ детерминировано (и почему):**

1. **`Math.random()`, `Date.now()`, `new Date()`.** **FACT:** страница открывается несколько раз в нескольких потоках, поэтому значения не совпадут между потоками. [4] → V8, ловить линтером (§8.6).
2. **Эмодзи.** **FACT:** *«Emojis are always rendered as-is by the operating system»* и различаются между ОС; *«When rendering in the cloud or in Linux in general, you will not get the same emojis as on your Desktop»*. [11] → **INFERENCE:** прямая угроза переносу рендер-воркера в облако (§2). Лечится только явным шрифтом эмодзи, поставляемым с проектом.
3. **Системные шрифты.** **INFERENCE:** любой шрифт, не поставляемый с проектом, резолвится ОС → разный рендер на разных машинах. Отсюда §8.5.
4. **Версия Remotion = версия Chrome.** **INFERENCE из [11]:** апгрейд Remotion меняет версию Chrome, а значит потенциально субпиксельный рендер текста и антиалиасинг. **Апгрейд Remotion обязан считаться изменением, инвалидирующим кэш кадров** — иначе AC4 сломается молча, и это худший вид поломки.
5. **GPU-путь.** **FACT:** дефолтный бэкенд в Remotion 5.0 — `angle`, который *«uses a compatible GPU when available»* с фолбэком на SwiftShader. [10] **INFERENCE:** «когда доступен GPU» = результат зависит от драйвера и наличия GPU, то есть от машины. Для AC4 это недопустимо → фиксируем `swangle` (софтверный растеризатор) в `renderProfile`.
6. **Кодирование.** **INFERENCE:** битовая идентичность выходного mp4 между запусками — сильное и не нужное нам требование (энкодеры могут содержать многопоточные недетерминизмы). **AC4 надо формулировать как равенство кадров, а не файлов** — см. §8.7.
7. **UNKNOWN.** Даёт ли headless Chrome одной версии **побитово** одинаковый кадр при одинаковом входе на одной машине, и стабильно ли это между запусками при разной загрузке системы. Официального утверждения об этом я не нашёл. Это **надо померить до того, как AC4 будет закодирован в тестах** (§10.2).

### 7.5 Чек-лист граблей: delayRender / таймауты / шрифты / staticFile

**delayRender**
* **FACT.** Дефолтный таймаут — 30 000 мс; меняется на уровне вызова (`timeoutInMilliseconds`) или глобально. [2][3]
* **FACT.** *«If a delayRender() call is not cleared within the timeout, the whole browser tab will be closed and the frame will be retried from scratch»*; есть `{retries: 1}`. [3]
* **PRACTICE.** Всегда передавать **label** — иначе в ошибке не видно, какой именно вызов завис.
* **PRACTICE.** Не вызывать на верхнем уровне модуля: это блокирует другие композиции. [3]
* **PRACTICE.** Хранить handle в `useState`, чтобы не плодить новый на каждый ре-рендер. [3]
* **INFERENCE.** У нас по V9 в рендере **нет сети**, поэтому `delayRender` должен остаться почти исключительно для загрузки шрифтов. Если в проекте появляется `delayRender` вокруг fetch — это баг архитектуры, а не тюнинг таймаута. Хороший инвариант для code review.

**Шрифты**
* **FACT.** С версии 2.2 Remotion сам ждёт загрузки шрифтов. [11] Есть `@remotion/google-fonts` и `loadFont()` из `@remotion/fonts` для локальных файлов. [11]
* **PRACTICE.** Шрифты — **файлами в репозитории**, а не с CDN Google Fonts: это V9 (нет сети), V10 (provenance/лицензия шрифта!) и детерминизм одновременно.
* **PRACTICE.** Грузить шрифты в одном общем модуле и ждать готовности до рендера. [11]
* **PRACTICE.** Эмодзи — только явным шрифтом (например Noto Color Emoji) в комплекте проекта, иначе см. §7.4 п.2.

**staticFile**
* **FACT.** `public/` должна лежать рядом с тем `package.json`, который содержит зависимость `remotion`, *«even if your Remotion code lives in a subdirectory»*. [6] **INFERENCE:** в монорепо на pnpm workspaces (§6 Charter) это неочевидно и укусит при первой же реорганизации пакетов — зафиксировать расположение в ADR.
* **FACT.** Кодирование имени — автоматическое, самому кодировать нельзя. [6]
* **FACT.** Путь не префиксовать самому; файл обязан лежать в `public/`. [6]

**Прочее**
* **FACT.** `colorSpace`: *«For best color accuracy, it is recommended to also use "png" as the image format»*; реальная конверсия цветового пространства выполняется только с v4.0.83. [2] **INFERENCE:** `png` заметно медленнее `jpeg` [9] — это размен «цвет против скорости», который надо решить осознанно и записать в `renderProfile`, а не получить случайно.
* **FACT.** `sampleRate` по умолчанию 48000 Гц: *«Match this to your source audio to avoid resampling artifacts»*. [2] **INFERENCE:** согласовать с частотой TTS-провайдера, иначе получаем ресемплинг на ровном месте — и он же испортит forced alignment из AC5.

## 8. Что заложить в архитектуру СЕЙЧАС, чтобы не переписывать на long-form

Это главный практический раздел. Каждый пункт — ответ на вопрос «что сломается, когда 60 секунд превратятся в 20 минут».

### 8.1 RenderIR — граница, ради которой всё затевается

Самое важное решение — **не «взять Remotion», а «не дать Remotion протечь в модель проекта»**.

```
ProjectModel (zod) ──compile──> RenderIR ──adapt──> RemotionAdapter ──> сегменты
                                   │
                                   └──adapt──> (будущий) CanvasAdapter / ffmpegAdapter
```

`RenderIR` — плоское, сериализуемое, renderer-agnostic описание: сцены, слои, тайминги **в кадрах** (не в секундах — производная от V1), ссылки на ассеты по checksum (V10), параметры эффектов, seed'ы. Правила:

* В `RenderIR` **нет ни одного импорта из `remotion`** и ни одного React-типа. Проверяется тестом на зависимости.
* React-компоненты Remotion — **только в адаптере**. Это тонкий слой «IR → JSX», а не место для бизнес-логики (V9).
* `RenderIR` сериализуется в JSON и является входом для хэша кэша (§8.3).

**Почему именно так (INFERENCE):** это единственная страховка от двух реальных сценариев — (а) AC2/AC3 не выполняются на реальном железе и нужен быстрый backend для draft-режима (кандидат C/D), (б) лицензионный риск §9.1 реализуется. В обоих случаях меняется адаптер, а не движок. Без этой границы оба сценария означают переписывание проекта.

### 8.2 Глава — единица рендера, кэша и параллелизма

V4 уже запрещает эффектам пересекать границу главы. Это надо превратить из декларации в исполняемый механизм:

* Компилятор `RenderIR` **валидирует** инвариант V4 и падает с внятной ошибкой, если эффект/звук/анимация пересекает `[chapter]`. Инвариант, который никто не проверяет, перестаёт выполняться примерно на тридцатом ролике.
* Каждая глава рендерится **своим вызовом рендера** — отдельный процесс, своя жизнь Chrome. Это прямо реализует рекомендацию Remotion «split up long renders into multiple parts» [10] и ограничивает последствия утечек памяти одной главой.
* Длина главы — предмет тюнинга (**UNKNOWN**, §10.3): короткие главы = лучше гранулярность AC3 и меньше пик памяти, но больше накладных расходов на старт Chrome и больше стыков.

### 8.3 Ключ кэша сегмента

```
segmentKey = hash(
  RenderIR[chapter]            // содержимое главы
  + assetChecksums[]           // V10: checksum ассетов, не пути
  + renderProfile              // §8.4
)
```

**INFERENCE — почему `renderProfile` обязан быть внутри хэша:** без него апгрейд Remotion (⇒ новая версия Chrome [11]) или смена `--gl` даст **валидный по кэшу, но визуально другой** сегмент, и в финальном ролике появится шов, который никто не заметит до просмотра на телефоне (DoD §8.5 Charter'а). Это ровно тот класс багов, который дорого ловить поздно.

### 8.4 `renderProfile` — всё, что влияет на пиксели, в одном версионируемом объекте

Не «настройки по умолчанию», а явная запись: версия Remotion, версия Chrome (из файла `VERSION` [11]), `--gl` (`swangle`), `concurrency`, лимиты обоих кэшей, `imageFormat`, `jpegQuality`, `colorSpace`, `codec`, `crf`, `gopSize`, `pixelFormat`, `sampleRate`, список шрифтов с checksum'ами, разрешение, fps.

Правило: **`renderProfile` меняется только осознанно и отдельным коммитом** — по той же логике, по которой Charter защищает сам себя.

### 8.5 Ассеты и шрифты — герметично

* Шрифты — файлами в репо/хранилище, с provenance и лицензией (V10 распространяется на шрифты, не только на картинки).
* Шрифт эмодзи — явный, в комплекте (§7.4 п.2).
* Ассеты ресайзятся на ingest под целевое разрешение (§7.2), имена — ASCII-safe/по checksum (§7.2).
* В рендере нет сети (V9) — это можно и нужно **проверять**: рендер под флагом, запрещающим внешние запросы, а `onBrowserLog` ловит попытки.

### 8.6 Детерминизм как исполняемое правило, а не как намерение

* ESLint-правило: запрет `Math.random`, `Date.now`, `new Date()`, `performance.now()` в пакетах рендер-пути. V8 без линтера — это пожелание.
* Все случайности идут через seeded `random()` [4], seed лежит в `RenderIR` (то есть попадает в хэш кэша).
* Запрет нестабильных сортировок — тоже V8; в компиляторе IR сортировки по составному ключу с гарантированным тай-брейкером.

### 8.7 AC4 проверять на кадрах, а не на файлах

**INFERENCE.** Тест детерминизма должен рендерить фикстурный проект дважды и сравнивать **декодированные кадры** (например, попиксельно или по перцептивному хэшу с нулевым порогом), а не байты mp4. Сравнение файлов даст ложные падения из-за метаданных/многопоточности энкодера и приведёт к тому, что тест отключат — то есть AC4 умрёт. До того, как порог зафиксирован, нужен замер §10.2.

### 8.8 Конвейер сборки — фиксируем форму сразу

```
для каждой главы:  render(muted) -> segment.ts   [кэшируется по segmentKey]
                                     │
аудио целиком:     PCM/WAV timeline ─┤            [V6: кодирование один раз]
                                     ▼
                   ffmpeg concat -c copy  ->  mux с аудио  ->  final.mp4
```

**INFERENCE.** Форма не меняется при переходе 60 сек → 20 мин: меняется только число сегментов. Именно поэтому её надо заложить сразу, даже когда глав всего две и кажется, что проще отрендерить одним куском. «Отрендерим одним куском, а сегменты добавим потом» — это и есть то переписывание, которого просили избежать.

### 8.9 Рендер-воркер за интерфейсом

Charter §2 разрешает позже вынести рендер в облако. Достаточно, чтобы вызов рендера сегмента был асинхронной функцией `(segmentKey, RenderIR[chapter], renderProfile) -> segmentFile` с локальной реализацией сегодня. Ничего больше сейчас проектировать не нужно (§5 anti-scope) — но и меньше нельзя, иначе вынос потребует хирургии.

## 9. Риски

### 9.1 РИСК №1 — лицензия Remotion (юридический, не технический)

Это самый серьёзный риск рекомендации, и он не решается кодом.

* **FACT.** Terms v5.0: Free License — *«Any User qualifying as an individual using the Remotion Software for personal or commercial use; an organization or team of individuals with up to 3 people; a non-profit or not-for-profit organization; or evaluating whether the Remotion Software is a good fit.»* [18]
* **FACT.** Там же определено **Automation**: *«Owning code that calls one of the following APIs or commands programmatically: `renderMedia()`, `renderStill()`, `renderFrames()`, … `npx remotion render` …»* [18]
* **FACT.** Определён **Render**: *«Outputting a video, an audio file, a still image, or an image sequence … Only successful renders count.»* [18]
* **FACT.** Коммерческие условия: Remotion for Automators — $0.01 за рендер при Minimum Spend $100/мес; Remotion for Creators — $25/мес за Seat; Enterprise — от $500/мес. [19]

**Где именно неопределённость.** Наш движок по определению «owns code that calls `renderMedia()` programmatically» — то есть он **является Automation** по букве определения. При этом соло-разработчик подпадает под Free License как *individual … for personal or commercial use*. Тексты дают два разных прочтения: (1) Automation — это лишь классификация *типа* Company License, и на право индивидуума на Free License она не влияет; (2) Automation сама по себе выводит из-под Free License.

**FACT о расхождении источников.** Юридический документ (Terms v5.0) перечисляет individual в Free License без оговорки про автоматизацию [18]; маркетинговая страница тарифов описывает Automators как трек для «automated video pipelines» [19]. Я **не берусь** трактовать это в чью-либо пользу — это вопрос к правообладателю.

**Что делать (действие, а не наблюдение):**
1. **Написать в Remotion и получить письменный ответ** по конкретному кейсу: «один человек, локальный рендер на своей машине, автоматизированный пайплайн, коммерческий YouTube-канал». Сделать это **до** написания кода адаптера, а не после.
2. До получения ответа считать риск открытым и **не убирать границу `RenderIR`** (§8.1) — она же является планом отхода.
3. Прикинуть худший сценарий: $100/мес Minimum Spend против стоимости своего рендерера (кандидат C) — при малых объёмах подписка почти наверняка дешевле недель разработки, так что даже реализация риска не убивает выбор. **INFERENCE.**

*Замечание.* Это единственное место, где я сознательно оставляю вопрос открытым вместо того, чтобы дать ответ: неверная трактовка чужой лицензии — это не техническая ошибка, а юридическая, и её нельзя закрывать «выводом из документации».

### 9.2 Остальные риски

| Риск | Оценка | Митигация |
|---|---|---|
| AC2/AC3 не выполняются на CPU без GPU | **Высокий, не проверен** | Спайк §10.1 **до** написания адаптера; draft-режим (ниже разрешение/fps, `--scale`) [9]; при провале — backend C для draft |
| OOM на long-form | Средний | §7.1 (явные лимиты) + §8.2 (глава = процесс) |

| Эмодзи/шрифты разъезжаются при выносе в облако | **FACT** [11] | Шрифты и эмодзи — файлами в комплекте (§8.5) |

## 10. UNKNOWN — что обязательно померить (спайки)

Ни одно из этих чисел я не выдумываю; все они требуют запуска на **вашем** ноутбуке.

### 10.1 Спайк «фикстура и бюджет кадров» — блокирующий, делать первым

Собрать минимальную композицию, близкую к реальной (фон-изображение + Ken Burns + субтитры по словам), и померить кадры/сек при `--gl=swangle` и разных `concurrency` (`npx remotion benchmark` [2]).

Бюджеты — арифметика от Charter (**INFERENCE**, при 1080×1920):

| Требование | Кадров | Лимит | Нужно кадров/сек |
|---|---|---|---|
| AC2: 60 сек @30fps | 1 800 | 15 мин | **≥ 2,0** |
| AC2: 60 сек @60fps | 3 600 | 15 мин | **≥ 4,0** |
| AC3: глава ~15 сек @30fps (draft) | 450 | 3 мин | **≥ 2,5** |
| Long-form 20 мин @30fps | 36 000 | — | 2 fps → ~5 ч; 5 fps → ~2 ч; 10 fps → ~1 ч |

**INFERENCE — важное наблюдение.** Ограничивает не AC2, а **AC3**: 2,5 кадр/с против 2,0. И на long-form при 2 кадр/с полный рендер — около пяти часов; это, возможно, приемлемо для ночного прогона, но означает, что **инкрементальность (§8.2–8.3) — не оптимизация, а обязательное условие пригодности**. Решение о fps (30 против 60) стоит принимать после этого замера: цена ошибки — двукратная.

### 10.2 Спайк «детерминизм» — блокирующий для AC4

Отрендерить фикстуру дважды на одной машине; сравнить декодированные кадры. Ответить: побитово или с расхождениями? Влияет ли `concurrency`? Влияет ли `--gl` (`swangle` против `angle`)? Результат определяет формулировку порога в AC4 (§8.7).

### 10.3 Спайк «длина главы»

Померить: время старта Chrome на сегмент, пик RSS против длины главы, деградация памяти на 20 последовательных сегментах (проверка утечек). Результат — рекомендуемая длина главы и решение, нужен ли рестарт процесса между сегментами.

### 10.4 Прочие UNKNOWN

* Реальная разница `swangle` против `angle` по скорости на вашем железе (стоимость выбора в пользу детерминизма).
* Применимость `combineChunks()` [7] к главам **разной** длины — рецепт Remotion описан для равных чанков; возможно, для глав придётся конкатенировать самим через ffmpeg. Проверить экспериментом.
* Стабильность рендера при работе ноутбука от батареи / при троттлинге (влияет на воспроизводимость таймингов, но не кадров).
